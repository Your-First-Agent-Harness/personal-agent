## 2. 练习 E1：证据归层与证据不足

**建议用时**：6 分钟，个人作答后两人互查。

### 题目

把下列陈述分别放到五层：①协议规范；②SDK/实现；③Server 生态；④企业采用；⑤实际互操作。随后回答“它能证明什么、不能证明什么”。

1. 2025-11-25 规范定义了 `tools/list`。
2. 某语言 SDK 出现在官方 SDK 页面。
3. 一个 Server 的元数据进入 Registry。
4. 一家企业在公开公告中宣布支持 MCP。
5. Client A 与 Server B 在 2025-11-25、stdio 下完成一组 Tools 测试。
6. 本仓库 D039 在新 Client 上完成一次独立 echo 调用。

### 参考答案

| 陈述 | 主要层级 | 可以证明 | 不能单独证明 |
| --- | --- | --- | --- |
| 1 | ① | 规范存在相应共同定义 | 所有 SDK 和 Server 已实现 |
| 2 | ② | 有官方列出的实现入口 | 功能完整、维护一致、跨语言一致；SDK tiers 仍需另查 |
| 3 | ③ | 有可发现元数据与相应发布流程 | Server 代码安全、活跃维护、业务权限正确 |
| 4 | ④ | 企业公开表达采用或支持意愿 | 所有产品、所有版本已实际互通 |
| 5 | ⑤，限受测组合 | A×B×版本×stdio×受测 Tools 用例的互操作 | 其他 Client、HTTP、Resources、未来版本或全行业 |
| 6 | ⑤，且只是仓库内定点恢复证据 | 新进程、新握手、独立调用能按 Demo 设计工作 | 通用自动重连、失败请求可安全重放、D040 已授课 |

**讲评重点**：一个陈述可能有次要层级，但答案必须先找它最直接支撑的结论。基金会的治理公告不要硬塞进第五层。

## 3. 练习 E2：版本、能力和错误边界

**建议用时**：8 分钟。

### 题目

假想 Client C 与 Server S 均声明支持 2025-11-25，初始化时只协商了 Tools。完成以下判断：

1. C 能否因为“版本相同”直接调用 `resources/list`？
2. S 返回一个合法 Tool Schema，是否说明 C 的模型提供商一定接受同一 Schema 的所有关键字？
3. 一次 `tools/call` 返回 `isError=true`，是否说明 stdio 已断开？
4. 请求超时后没有收到响应，是否说明工具没有执行？
5. 2026-07-28 规范定义了 `server/discover`，能否因此把本仓库 D035 Client 标成已支持该方法？

### 参考答案

1. **不能**。协议版本协商与能力协商不同；未协商的 Resources 不得使用。本仓库也未实现 Resources。
2. **不能**。需要检查模型私有接口的 dialect、关键字子集、strict 约束和 SDK 转换。S24 的 best-effort schema conversion 是现实反例。
3. **不能**。这是已到达 Client 的工具结果，属于业务/工具执行失败语义；传输断开是另一类错误，恢复策略不能混用。
4. **不能**。结果处于未知状态，Server 可能已经执行。副作用工具需要幂等、事实查询或对账，不能盲目重放。
5. **不能**。后续规范能力不是旧实现的回溯属性。本仓库明确限定为 2025-11-25、stdio、Tools 子集。

**加分题**：为什么“Server 有 Tools capability”仍不能批准一次退款？
**答案**：能力协商只说明协议功能存在，不说明当前用户、租户、订单状态、金额和本次审批满足业务权限。

## 4. 练习 E3：传输选择与会话恢复

**建议用时**：8 分钟，小组完成。

### 场景

- **A**：开发者笔记本上的只读文件搜索；Server 由 Host 启动，不需要跨机器访问。
- **B**：多团队共享的订单查询；公司已有 SSO、API 网关、集中审计和远程部署。
- **C**：一个创建订单的远程工具；请求超时后客户端没有收到响应。

### 任务

1. 为 A、B 分别选择 stdio 或 Streamable HTTP，写两项收益和两项新增风险。
2. 为 A 写一个进程关闭测试，为 B 写一个会话/身份测试。
3. 为 C 写出超时后的处理顺序，说明为什么不能直接重放。

### 参考答案

**A 更自然地倾向 stdio**，但不是强制答案：

- 收益：无需暴露网络端口；Host 可直接管理子进程生命周期。
- 风险：恶意或错误的启动命令/依赖可访问本机；stdout 污染、环境变量泄露、子进程不退出会破坏客户端。
- 关闭测试：Client 关闭 stdin 后等待；若测试 Server 故意不退出，应按既定超时升级 SIGTERM/SIGKILL，且最终无遗留进程。日志写 stderr，不破坏协议帧。

**B 更自然地倾向 Streamable HTTP**：

- 收益：复用现有远程部署、身份和审计基础设施；多团队无需各自启动相同 Server。
- 风险：会话劫持、错误受众 token、Origin/DNS rebinding、网络断线与重复消息；集中服务也扩大权限影响面。
- 会话/身份测试：使用错误 audience、过期凭证、不同租户和被终止会话分别请求，均应被明确拒绝；审计能关联真实用户而不是只有 session id。

**C 的安全处理顺序**：

1. 把本次调用标为“结果未知”，保留调用 id、业务幂等键和审计上下文；
2. 不自动重放创建订单；
3. 通过独立只读接口按幂等键或业务标识查询订单事实；
4. 若无法确定，进入人工核对/对账流程；
5. 只有业务幂等契约明确且重试策略允许时，才设计新的受控尝试。

传输恢复与业务恢复是两层。新连接不自动证明旧请求未执行。

## 5. 练习 E4：Schema 与结果适配

**建议用时**：10 分钟。

### 题目

假想 MCP Server 发布以下教学节选：

```json
{
  "name": "refund_order",
  "inputSchema": {
    "type": "object",
    "properties": {
      "orderId": { "type": "string" },
      "amountMinor": { "type": "integer", "minimum": 1 },
      "reason": { "type": "string" }
    },
    "required": ["orderId", "amountMinor", "reason"],
    "additionalProperties": false
  }
}
```

回答：

1. 这是否已经是一个“模型一定可用、用户一定获批、退款一定成功”的完整契约？列出缺失信息。
2. 如果目标模型接口的 strict 转换不支持某个嵌套组合关键字，应该静默丢弃约束吗？
3. MCP `structuredContent` 存在时，能否省略业务结果校验？
4. `isError=true`、JSON-RPC error、进程退出分别表示什么？能否共用“直接重试”策略？

### 参考答案

1. **不是完整契约**。Schema 只描述部分输入形状。还需要：调用者和租户身份、订单归属、订单是否可退款、可退金额与币种、审批、幂等键、超时、结果未知处理、成功输出、业务错误、审计和副作用说明。模型接口还可能需要 Schema 转换。
2. **不应该静默丢弃**。应显式报告不支持项，采用经过审查的等价转换，或拒绝该工具进入 strict 路径；保留原 Schema 也要让调用方知道严格性未得到保证。S24 的 best-effort 行为不能解读成所有约束自动保留。
3. **不能**。结构化只是表示形式，仍需按业务契约验证状态、金额、对象和租户。可选 `outputSchema` 有帮助，但不能替代业务校验和权限。
4. `isError=true` 是工具结果中的失败；JSON-RPC error 是协议层已返回错误；进程退出是传输/生命周期故障。三者不能共用直接重试。尤其超时和退出时，旧请求执行状态可能未知。

## 6. 练习 E5：安全威胁建模

**建议用时**：12 分钟。

### 题目

一个 Host 从 Registry 发现“财务助手”Server，看到 namespace 已验证。Server 工具描述写着“只读、安全”，并要求 Host 把当前用户的 OAuth token 原样转发。实际工具可以读取所有租户，且结果中可能包含网页文本。

请至少找出六项风险，并为每项写控制。进一步回答：以下哪些事实可以消除风险？

- A. Server 使用 MCP；
- B. 工具通过 JSON Schema 校验；
- C. Registry namespace 已验证；
- D. 以上都不能单独消除。

### 参考答案

| 风险 | 控制示例 |
| --- | --- |
| 工具描述不可信，可能误导模型或操作者 | 把描述当不可信数据；独立审查实际权限和行为，不从描述授权 |
| Token passthrough / 错误受众 | 校验 issuer、audience、scope；按服务使用合适凭证或交换机制 |
| Confused deputy，Server 替调用方越权读取 | 传递可信用户/租户上下文，Server 再授权，默认拒绝跨租户 |
| 过宽 scope | 最小权限、短期 token、按工具/资源拆分权限 |
| Prompt injection 来自网页结果 | 内容隔离与标记、最小上下文、敏感动作审批，不把结果文本当指令 |
| Registry 身份被误当安全审计 | 锁定版本与摘要、代码/依赖/安装脚本审查、扫描和来源准入 |
| 审计只记录 Server，不记录真实用户 | 记录用户、租户、工具、参数摘要、审批和结果关联 |
| 供应链更新引入新行为 | 固定版本、变更审查、灰度和回滚，不自动跟随未审查版本 |

答案为 **D**。MCP、Schema 和 namespace 各自解决一部分问题，都不能独立替代端到端威胁建模。

## 7. 练习 E6：MCP、直连还是等待

**建议用时**：12 分钟，每组选择一个案例。

### 案例

**案例 1：两个内部只读接口**
团队只有两个稳定 OpenAPI 服务，现有 SDK、SSO、网关和测试成熟，没有第三方 Server 复用需求。

**案例 2：跨团队工具平台**
六个团队维护独立工具，多个 Agent Host 需要统一发现；安全团队能参与授权和审计，但当前只验证了一个版本组合。

**案例 3：高副作用财务写操作**
外部 Server 声称支持 MCP，但无法清楚说明 token 受众、租户隔离、幂等和审计；业务方希望立刻自动退款。

### 任务

用决策句式给出选择，列两项收益、两项成本、三项上线/继续试验前测试，以及一个改判条件。

### 参考答案

**案例 1：倾向直连 API。**
收益是调用链短、复用现有成熟控制；成本是未来若工具供给增多可能要新增统一层。测试可聚焦现有 OpenAPI 契约、权限和错误语义。若未来出现多个独立工具团队，并且维护私有适配的成本超过 MCP 层成本，可重新评估 MCP。不能说“直连永远最好”。

**案例 2：倾向有边界地采用 MCP，而不是一次性全量迁移。**
收益是统一发现和复用；成本是版本、传输、Schema 和权限适配。先做固定 Client×Server×2025-11-25 或实际目标版本的 Tools 测试，再补安全、失败恢复和升级测试。若关键组合持续不能互操作，或权限模型无法统一，应缩小范围或改用直连。

**案例 3：应暂缓生产自动化。**
不是“等待 MCP 成熟”这么笼统，而是等待该集成满足明确门槛：token 受众和租户授权可验证；退款幂等和结果未知处理可验证；审批、审计和供应链审查通过。未满足前，即使 Demo 能调用也不应自动退款。

## 8. 练习 E7：换掉 MCP 的迁移盘点

**建议用时**：8 分钟。

### 题目

把下列资产分为“尽量保留”“在适配层替换”“重新验证”三列；每项可进入多列，但要说明原因。

- 文件读取业务 Handler
- stdio 子进程管理
- 工具参数的领域校验
- MCP `initialize` 与 capability negotiation
- 租户审批策略
- MCP `content` 到本地 ToolResult 的映射
- 退款幂等键与事实查询
- 订单成功/失败黄金测试
- 第三方 Server 的版本锁定与供应链审查

### 参考答案

| 资产 | 尽量保留 | 在适配层替换 | 重新验证 |
| --- | --- | --- | --- |
| 文件读取 Handler | 保留领域输入/输出和副作用边界 | 只改调用入口 | 在新协议下跑读写与错误用例 |
| stdio 子进程管理 | 通常不绑定到业务层 | 大多替换 | 新传输的关闭、隔离和资源清理 |
| 领域校验 | 保留不变量与错误语义 | 必要时转换 Schema 表示 | 目标 Schema 方言和业务校验共同验证 |
| 初始化/能力协商 | 不保留为实现无关业务逻辑 | 按新协议重写 | 版本、能力和错误组合测试 |
| 租户审批策略 | 保留策略与审计语义 | 重新绑定新身份上下文 | 跨租户、过期凭证、审批范围 |
| 结果映射 | 保留本地结果语义 | 替换 MCP 信封转换 | 成功、工具错误、协议错误和断线 |
| 幂等键/事实查询 | 高度保留 | 重接重试与恢复入口 | 超时、重复请求、对账 |
| 黄金测试 | 保留输入和业务期望 | 替换传输壳 | 全量重跑，不因旧测试通过而省略 |
| Server 版本与供应链审查 | 保留准入流程和证据格式 | 更新新实现来源与锁定信息 | 新依赖、新产物和新权限 |

**结论**：可迁移性来自业务与协议解耦，不来自“使用了标准”这句宣传。

## 9. 练习 E8：综合架构评审

**建议用时**：课后 20–30 分钟。

### 题目

为你熟悉的一个 Agent 项目写一页评审，必须包含：

1. 工作负载、数据敏感级别和副作用；
2. 明确 MCP 版本、传输和能力；若不用 MCP，写现有接口边界；
3. 五层证据各一条，缺失就写“未验证”；
4. 一张从模型调用意图到业务系统的数据流图；
5. 认证、授权、业务权限、审批、审计和供应链控制；
6. 版本升级、断线、超时和结果未知测试；
7. 选择 MCP/直连/暂缓的条件化结论；
8. 一个反方观点、一个改判条件和一份可迁移资产清单。

### 参考评价量规（100 分）

| 维度 | 分值 | 合格表现 |
| --- | ---: | --- |
| 范围与版本 | 15 | 明确版本、传输、能力和未实现项，不写无日期“最新” |
| 分层证据 | 15 | 规范、实现、生态、采用、互操作不混用；未知项诚实标记 |
| 边界比较 | 10 | 正确区分 function calling、MCP、REST/OpenAPI、A2A |
| 安全 | 20 | 认证不等于授权，覆盖注入、会话、token、供应链和副作用 |
| 失败与版本演进 | 15 | 不盲目重放；有能力协商、升级与兼容测试 |
| 决策与反方 | 15 | 有条件、有成本、有反方和可观察改判条件 |
| 可迁移性 | 10 | 业务资产与传输/握手/信封分离，迁移后重新验证 |

**不合格红线**：伪造行业采用数字；把仓库 Demo 外推为全行业；把 Registry 条目当安全证明；主张副作用请求断线后总是自动重试；隐瞒未实现能力。

## 10. 退出题与参考答案

### 题目

1. 为什么公开规范和基金会治理仍不能证明实际互操作？
2. 为什么有效 OAuth token 和合法 JSON Schema 仍不能批准一笔业务写操作？
3. 为你的项目选择 MCP、直连或暂缓，并写一个会改变决定的证据。

### 参考答案要点

1. 规范和治理位于第一层与制度层；实际互操作要求具体 Client×Server×版本×传输×能力组合通过测试，还需检查实现分级和适配。
2. token 只提供某种身份/授权上下文，Schema 只检查形状；业务写仍需租户与对象权限、状态机、金额、审批、幂等和审计。
3. 没有唯一字母答案。合格答案必须写工作负载、版本/能力、两项成本、安全门槛和可观察改判条件；只写“MCP 是趋势”不得分。

## 11. FAQ：讲师备课答案

### Q1：MCP 已经是正式国际标准了吗？

本课不使用这种笼统表述。可核验事实是：它有公开版本化规范、公开治理和跨组织协作，Linux Foundation 于 2025-12-09 宣布 AAIF，MCP 是创始贡献项目之一。是否满足某个特定标准组织的正式定义，要按该组织程序另行核实；这不影响本课的五层工程分析。

### Q2：有基金会治理，是否就说明它不会是过渡方案？

不能。治理提高公开演进和协作的可预期性，但不消除版本迁移、场景不匹配和替代技术。一个协议可以治理开放，同时仍只是某系统的暂时适配层。

### Q3：MCP 和 function calling 谁替代谁？

它们主要位于不同边界。function calling 让模型表达调用意图；MCP 让 Host/Client 发现并调用外部能力。Host 经常要把 MCP Tool 转成模型私有工具定义，再把结果转换回来，所以二者可以组合。

### Q4：都用 JSON Schema，为什么仍要适配？

因为方言、关键字子集、strict 规则、额外字段、嵌套组合、引用和结果信封可能不同。S24 的 `convertSchemasToStrict` 是 best-effort，正好说明实际 SDK 需要转换且不能保证全部成功。

### Q5：MCP 会不会取代 REST/OpenAPI？

不能从协议存在推出全面取代。少量稳定内部 HTTP API 用直连可能更简单；MCP 增加统一发现和 Agent 生态边界。业务 API 仍可在 MCP Server 后面继续以 REST/OpenAPI 存在。

### Q6：MCP 和 A2A 是竞争关系吗？

不完全是。MCP 偏 Agent 到工具/资源，A2A 偏独立 Agent 之间协作，核心有 Agent Card、Task、Message、Part、Artifact。一个系统可组合使用。本课只划边界，不评价二者采用前景。

### Q7：stdio 和 Streamable HTTP 哪个更标准？

两者都是规范中的传输方式，选择看部署边界。stdio 适合本地子进程；HTTP 适合远程服务，但会增加会话、身份和网络安全工作。不能从“HTTP 更通用”推出所有场景都应选 HTTP。

### Q8：版本相同是否就能互通？

还需能力协商、传输一致、Schema/结果适配、错误语义和实际测试。版本相同是重要前提之一，不是完整互操作证明。

### Q9：Registry 中的 Server 是否可以默认可信？

不可以。namespace 验证和元数据发现有价值，但不等于代码、依赖、安装脚本和运行时权限已经安全审查。仍需版本锁定、来源准入、扫描和最小权限。

### Q10：MCP 是否内置了完整用户权限系统？

MCP 有授权与安全规范，但不能替代 Host、Server 和业务系统共同实现认证、授权、租户权限、审批与审计。有效 token 不等于对某个业务对象有权限。

### Q11：断线后应该自动重连并重试吗？

重连和重试要分开。新连接可以恢复服务可用性，但旧请求是否执行未知。副作用工具必须先依靠幂等、事实查询和对账，不能默认重放。D039 的恢复调用是新 Client 上的独立 echo，不是失败请求重放。

### Q12：本仓库是否已经实现完整 MCP？

没有。D035–D039 只实现 `2025-11-25 + stdio + tools` 子集。未实现 Streamable HTTP、Resources、Prompts 和 2026-07-28 的新协商/兼容机制等，不应从规范能力反推仓库能力。

### Q13：如果未来不用 MCP，前期投入会全部浪费吗？

不一定。业务 Handler、领域 Schema/校验、权限与审批、幂等、审计语义、测试夹具和业务文档都可保留；传输、握手、发现、协商和结果映射更可能需要替换。保留程度取决于适配层是否薄且业务是否解耦。

### Q14：课程到底建议采用还是不采用？

课程给的是决策方法，不给绝对建议。需要多方工具复用、目标组合验证充分且能承担安全运维时，MCP 更有吸引力；少量稳定内部 API 可优先直连；关键安全和互操作未验证时应暂缓生产放量。

### Q15：为什么不在 README 放公开课视频或学员评价？

因为本轮没有实际授课、没有录屏、没有学员反馈。课程材料已准备不等于活动已发生。任何未来真实回放和反馈都应在实际产生后记录来源，不能预先填入。
