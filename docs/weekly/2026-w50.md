## D027 复盘：先统一“当前工具是什么”

### 实际实现

- `Tool` 保持 Schema 与 execute 同对象；Registry 另外保存版本、metadata 和条目配置。
- `discover()` / `describe()` 给宿主发现信息，`list()` 只向模型提供名称、描述和参数 Schema。
- 未声明版本显示 `unversioned`；同名只能替换，不能注册重复项。
- 注册/替换先验证，非法替换不破坏旧工具；注销影响后续发现和执行。
- Loop 从整个 run 固定一次工具数组改为每轮重新 `list()`。

### 证据与结论

`test/d027-tool-registry.test.ts` 的 11 个测试覆盖参数化非法注册，而不仅是 5 个 `it` 标题。测试断言了发现结果、旧版可用性、替换后执行和注销后的 `UNKNOWN_TOOL`。

**结论**：动态发现的关键不是“能换函数”，而是发现、执行和条目配置都指向同一个 Map 条目。按轮刷新比整 run 固定更适合撤销和修复，同时保留单次模型请求内的 Schema 稳定。

### 遗留边界

- version 是字符串元数据，不是 SemVer 协商、灰度或多版本共存。
- 替换/注销不强杀已开始的调用；替换会创建新的韧性状态。
- 未深冻结工具和 Schema，可信调用方不应注册后原地修改；不是恶意代码沙箱。
- Map 按名称唯一，不支持不同租户各持一个同名实现。

## D028 复盘：错误必须在副作用之前变得可修复

### 实际实现

- 注册时递归检查 Schema 形状，根参数必须是 object。
- 执行前支持对象、数组、字符串、数值、整数、布尔、null，以及 required、items、additionalProperties、长度、数值范围、enum、uniqueItems 等当前子集。
- 嵌套错误报告 `$.members[1].name` 这类完整路径和修复提示。
- 合法值原样交给 execute；不做 trim、强转、默认填充或未知字段自动删除。
- 无效参数在 execute 前返回 `INVALID_ARGUMENTS`；D029 接入后也先于敏感确认。

### 证据与结论

`test/d028-schema-validation.test.ts` 的 35 个测试覆盖 13 类执行前参数失败、合法嵌套值、数组/null/Unicode/数值边界、15 类非法 Schema、替换回滚及 5 个内置工具注册。`run_command` 的空命令和 timeoutMs 越界在 spy execute 前被拦截。

**结论**：统一递归校验的价值是“同一套路径语言 + 不进入副作用”，不是支持越多关键字越好。当前零新增依赖的子集足以覆盖内置工具，但必须明确它不是完整 JSON Schema。

### 遗留边界

- 未实现 `$ref`、组合 Schema、pattern、format，也不保证模型提供商接受所有 Schema。
- 未知字段默认允许；只有 `additionalProperties: false` 才拒绝。
- integer 不是安全整数校验；业务不变量仍需工具自身负责。
- `INVALID_ARGUMENTS` 虽标记可修复，但自动重试禁止直接重放，需模型/调用方先改参数。

## D029 复盘：不可见不等于不可调用，批准不能成为永久能力

### 实际实现

- 白名单未配置表示不额外限制，空数组表示全禁；发现与直接执行使用同一可见性策略。
- 共享工具与当前 Registry 租户工具可见，其他租户工具不可见；未配置租户不默认开放专属工具。
- 调用方伪造的 `tenantId` 被可信策略覆盖，不能借上下文越权。
- sensitive 工具每次逻辑 execute 都请求确认；回调缺失、拒绝和异常均不执行。
- 确认请求带 callId、工具名、校验后的原始参数和可信租户。
- 顺序为可见性 → JSON → Schema → 确认，权限拒绝也能作为 tool 消息回喂。

### 证据与结论

`test/d029-permissions.test.ts` 的 10 个测试包含坏 JSON 直接打隐藏工具、tenant spoofing、连续两次调用一批准一拒绝、确认后端秘密脱敏，以及权限失败后 Loop 第二轮正常完成。

**结论**：权限必须同时作用于 list/discover/describe 和 execute；只做模型侧隐藏不够。先校验再确认既减少无效审批，又让批准绑定到可理解的具体参数。

### 遗留边界

- 每次确认对应一次逻辑调用；若显式开启内部自动重试，同一批准覆盖其所有尝试。
- 进程内 tenantId 不是认证系统，没有持久授权、审计、跨进程隔离或同名多租户目录。
- 确认回调会接触原始参数，宿主 UI/日志仍须防泄密。
- 工具返回内容和主动构造的错误消息没有通用秘密扫描，不能把“未知异常脱敏”等同于全链路脱敏。

## D030 复盘：韧性不是无限重试，而是限制每次失败的传播

### 实际实现

- 每次尝试独立 timeoutMs 和子 AbortController；外部取消优先，迟到结果不能覆盖第一次 settle。
- maxRetries 默认 0；仅幂等工具或明确承担非幂等风险时，对可重试故障做指数退避。
- maxQueue 默认 0；配置队列后仍有长度与等待上限，取消/超时等待会移除等待者。
- 每个 Registry 条目独立限流和熔断；逻辑调用持有许可直到重试结束。
- 熔断按逻辑调用最终结果计数；冷却结束仅允许一个 half-open 探针，成功关闭、失败重开。
- 未配置 resilience 时仍直接调用，保留旧 signal 身份和结果对象。

### 证据与结论

`test/d030-resilience.test.ts` 的 40 个测试覆盖 5 组超时/取消、6 组重试、5 组限流、参数化熔断排除项、单探针与重开、非法配置和 Loop 集成。关键断言不仅是错误码，还包括实际尝试次数、迟到 rejection、队列移除、探针期间其他调用快速失败，以及坏工具与健康工具结果都回喂。

**结论**：四个机制必须共同理解：超时约束单次尝试，重试约束副作用，队列约束等待，熔断约束故障扩散。把“每个逻辑调用只计一次熔断失败”与“内部重试仍持有同一许可”结合，才能避免重试放大并发和故障计数。

### 遗留边界

- 每尝试超时不是总 deadline；排队、退避和全部尝试还受外部 signal 约束。
- AbortSignal 是协作式的，通用超时不能保证强杀无视 signal 的 Promise、子进程或远端工作。
- 退避没有 jitter/Retry-After，队列没有优先级；状态和故障计数不跨 Registry 或进程。
- 限流/熔断拒绝不会在当前执行器内立即自动重试，需调用方稍后发起新逻辑调用。
- fake timers 能验证状态转换，不能证明真实时间性能、生产并发或外部依赖恢复能力。

## 跨日复盘结论

### 做对了什么

1. **顺序是设计的一部分**：权限在参数解析前保护隐藏信息，参数校验在确认前减少无效审批，确认在 execute 前阻断副作用。
2. **安全与韧性不混用**：权限/参数/取消错误不自动重试、不烧断工具；真正可恢复故障才进入有条件下重试和熔断。
3. **默认可解释**：不重试、不排队、不增加 Registry 超时，旧式注册继续可用；高风险能力需要显式开启。
4. **失败仍是数据**：D029 的权限拒绝和 D030 的最终超时都回喂，Loop 能处理健康工具并继续；连续错误和外部取消仍保留终止权。
5. **测试观察实际副作用**：spy execute、尝试次数、队列与探针状态比单看快照更能证明边界。

### 不能从本周交付推出的结论

- 不能推出支持完整 JSON Schema、版本兼容协商或插件市场。
- 不能推出完成生产 IAM、多租户安全沙箱、持久审批或审计。
- 不能推出任何 Promise/进程都能被超时强杀，或分布式实例会共享限流/熔断。
- 不能推出真实模型一定会正确修复参数、遵守白名单或抵御工具输出提示注入。
- 不能把覆盖率当作外部系统可靠性，也不能把文档定稿当作 v0.3 已发布。

### 后续需要单独决策的边界（D031 不实施）

1. 总调用预算、随机退避、指标与跨实例状态是否需要引入。
2. 工具输出和确认 UI 的秘密保护、提示注入隔离与持久审计如何设计。
3. 需要完整 Schema 时，采用标准校验器还是继续维护子集。
4. 需要多版本/多租户同名工具时，Registry 键与发现协议如何迁移。

这些是复盘识别出的边界，不是本日新增需求，也不提前展开 D032。
