## 2. 四层设计为什么这样取舍

### 2.1 D034：先限制协议范围，再谈“支持 MCP”

MCP 不是“写一个 JSON 接口”就完成。先确定 initialize→initialized→tools 的生命周期，才能避免未初始化调用、版本混用、通知误回复和关闭语义发明。

选择 stdio ndjson 的理由：

- 与本项目本地子进程模型一致，零新增运行时依赖即可验证。
- 一行一个 JSON-RPC 帧，能真实处理跨 chunk、多帧、CRLF 和 parse error。
- stdout/stderr 职责清晰：前者是协议，后者是诊断。
- stdin 结束就是传输关闭信号，不另造规范外的 shutdown RPC。

代价是当前不具备 Streamable HTTP、远程认证、多 Client 和其他 MCP 能力。文档必须说“支持一个子集”，不能泛称完整 MCP。

### 2.2 D035：拥有 Client 状态机，换取可控的失败语义

手写 Client 的重点不是发出 `tools/call`，而是管理 `idle→connecting→ready→closing→closed`、request id、pending 表和子进程。

主要取舍：

- initialize 响应必须精确回到 `2025-11-25`，宁可报 `VERSION_UNSUPPORTED`，不静默混用协议。
- 调用工具前检查 `capabilities.tools`，把能力缺失与业务错误分开。
- `listAllTools()` 有 100 页上限，避免循环游标；保留单页 API 给调用方控制。
- 超时/取消发送取消通知，但不谎称远端工作一定停止。
- stderr 有界保留，stdout 非 JSON 立即视为协议错误；关闭有 stdin→SIGTERM→SIGKILL 的有界路径。
- 子进程环境默认空白，示例只白名单传 PATH/HOME 等，避免继承全部凭证。

收益是错误码、资源清理和依赖都可审计；成本是只实现当前子集，重连、完整通知生态和其他传输不在本仓库能力内。

### 2.3 D036：Server 是 Registry 的协议投影，不是第二套工具系统

自有 Server 同时接收 `registry` 与 `toolNames`：前者提供真实描述、Schema、策略和执行，后者决定本次会话愿意暴露什么。

关键映射：

```text
Tool.name/description/parameters → MCP name/description/inputSchema
MCP arguments object            → Registry ToolCall.arguments JSON 字符串
ToolResult.content/isError       → MCP content/isError
ToolResult.error                 → structuredContent.error
```

这样 Schema 校验、敏感工具确认、文件错误和路径边界只有一份实现。未知或未授权工具按 JSON-RPC `-32602` 处理；工具内部可预期的失败用 `result.isError:true`，两者不能混为一谈。

读循环不等待长工具，因此并发调用可以乱序完成，但必须按原 id 回复。取消与关闭传真实 AbortSignal 并抑制迟到响应；对于不监听 signal 的 Tool，Server 仍无法强制收回 Promise。

安全示例只暴露两个只读文件工具，并使用独立临时目录。没有为了演示把 shell、写文件或生产凭证一起暴露。

### 2.4 D037：适配层保持 Agent 契约，差异留在边界

直接把所有远端工具透传给模型看似省事，却会让 local/MCP 的模型提示、权限和路径含义漂移。当前选择显式投影：

- 本地始终只有 `read_file/list_dir`。
- MCP 远端必须有 `read_file/list_directory`，缺一个就关闭并失败。
- `list_dir` 到 `list_directory` 的改名只发生在适配层。
- 模型仍给工作区相对路径；适配层先做本地越界检查，再产生远端需要的绝对路径。
- 远端即使提供 `write_file`，也不会进入 Agent Registry。
- 初始化失败、关闭、超时和业务错误都转成已有 ToolResult 语义。

代价是需要维护名称和参数映射，而且官方目录输出与 local 不同。D037 证明的是“同一 Registry 接口和同一任务可完成”，不是“两个后端所有输出逐字节相同”。

## 3. 本周完整数据流

```text
模型 ToolCall
  → ToolRegistry（同一描述、Schema、策略）
  → local Tool
     或
  → MCP 投影（改名/路径映射）
  → StdioMcpClient
  → ndjson stdio
  → 外部 filesystem Server

外部 Client / 官方 Inspector
  → ndjson stdio
  → McpStdioServer
  → 同一个 ToolRegistry
  → 自有只读工具
```

两条方向共同复用的是工具契约和错误语义，而不是复用一个“既能 Client 又能 Server”的巨型类。Client、Server、投影各自有清晰生命周期，最后用 `try/finally close()` 汇合资源管理。

## 5. 已知限制与后续使用提醒

1. **协议限制**：只有 `2025-11-25`、stdio、tools；不要按完整 MCP SDK 能力设计上层。
2. **会话限制**：Client 不可重连，Server 是单 Client stdio；没有网络认证和多租户边界。
3. **发现限制**：自有 Server 不分页、不动态通知；外部分页有 100 页保护。
4. **内容限制**：自有 Server 不声明 outputSchema；投影会把非文本块序列化拼接，local/MCP 文本格式不保证一致。
5. **取消限制**：AbortSignal 需要 Tool 合作；超时只结束本地等待，迟到响应和清理必须谨慎处理。
6. **安全限制**：路径检查不是完整 OS 沙箱；外部 Server、npx 制品、环境变量和 stderr 都需要最小权限与脱敏。
7. **环境限制**：D035/D036/D037 的外部包需要 npm 网络或可信缓存；D037 用确定性模型，不证明真实模型质量。
8. **后端覆盖**：当前只适配官方 filesystem 的读文件/列目录，不代表任意 MCP Server 都能零配置替换 local。

## 6. 本周结论

这周最重要的不是“能连上一个 MCP Demo”，而是建立了四条可复用约束：

- 协议版本、初始化、通知和关闭必须显式。
- Client 与 Server 都要把并发、错误和资源生命周期当作主体设计。
- Registry 是工具契约的单一来源，MCP 只做协议投影。
- 双后端切换必须显式处理名称、参数、路径和权限差异，不能以“同协议”为由假设完全等价。
