## 0. 讲师一页速览

### 课程信息

- **时长**：90 分钟，不安排中场休息；互动时间已经计入。
- **对象**：会把 HTTP API 包成函数，但正在设计 Agent 工具层的开发者、架构师和产品工程师。
- **先修**：理解 JSON、HTTP 方法和基本权限概念；不要求读过本项目源码。
- **核心问题**：40 个 API 是做成 40 个工具、1 个工具，还是按任务与风险重新划定边界？
- **本案例答案**：16 个。它是这套虚构业务在本课约束下的一种可审查方案，不是所有系统的固定比例。
- **一句话主线**：**API 是系统之间的传输边界；Agent 工具是模型可理解、调用方可授权、运行时可治理的任务边界。**

### 学完能做什么

学员离场时应能独立完成四件事：

1. 给一组 API 建立无遗漏、无重复的 API→工具映射；
2. 用任务内聚、读写、权限和失败语义解释每一次合并或拆分；
3. 为每个工具写出入参、成功输出、副作用、确认、幂等、重试、超时和错误契约；
4. 识别“40=40”“万能 API”“所有失败都重试”“模型传 tenantId”等反例。

## 2. 5–15 分钟｜API 不是工具：先认识执行边界

### 2.1 三个定义

**讲师稿：**

> API 描述服务怎样被访问；函数描述代码怎样被调用；Agent 工具描述模型能请求什么任务，以及宿主允许这次请求穿过哪些治理边界。三者可以相关，但不必一一对应。
>
> 一个好工具至少要同时回答八个问题：做什么、需要什么参数、成功返回什么、有没有副作用、谁能调用、是否逐次确认、重复或超时怎么办、失败怎样回喂。只写 `fetch(url)` 只回答了其中很小一部分。

板书并逐项解释：

```text
任务契约：name + description + parameters + execute
治理契约：白名单 + 租户 + sensitive 确认
韧性契约：每尝试 timeout + 有界重试/限流/熔断
对话契约：ToolResult 回喂 + 连续失败停止
```

### 2.2 D027–D032 的真实基线

以下不是虚构商城能力，而是本仓库已有机制。讲师可打开[ADR-001](adr/0001-failure-semantics.md)核对。

| 课程日 | 已有真实机制 | 对工具粒度的约束 |
| --- | --- | --- |
| D027 | `Tool` 同时持有 name、description、parameters、execute；Registry 同名唯一，按轮 `list()` 发现 | 合并后仍要是一个可理解、可独立治理的条目 |
| D028 | 执行前 JSON 解析与递归 Schema 校验，错误带参数路径 | Schema 是第一道门，但不能替代业务不变量 |
| D029 | 工具白名单、租户可见性、可信 tenantId、敏感工具逐逻辑调用确认 | 权限差异是拆分理由；sensitive 是条目级，不是 action 级 |
| D030 | 每次尝试超时、默认不重试、有条件下重试、有界限流、half-open 熔断 | 同一工具的动作共享韧性配置，要检查最保守共同分母 |
| D031 | ADR 明确调用顺序、失败回喂和 trade-off | 设计要记录代价，不能只给“最佳实践”口号 |
| D032 | 恰好 10 个真实工具；正常任务通过真实 Loop 串联 9 个 | 多工具链要验证参数来自上一步结果，而非只数注册数量 |

补充真实边界：

- 每轮重新发现工具，单次模型请求使用同一批 Schema；同一轮多个 ToolCall 当前串行执行。
- 可预期工具失败转成 `ToolResult` 回喂；成功清零连续错误计数，默认连续 3 次工具错误停止。
- 模型提供商异常与工具失败不同，不伪造成工具结果。
- D032 的 Provider 是离线脚本化编排，不证明真实模型会自动规划本课 16 个工具，也没有公开课录屏。

### 课堂检查

问：“如果一个工具叫 `manage_commerce`，里面既有商品搜索又有扣款，当前 Registry 会给整个条目配几套 sensitive 和重试策略？”

**答案**：一套。sensitive、韧性和可见性都挂在 Registry 条目上，不会根据 `action="search"` 或 `action="capture"` 自动切换。

## 3. 15–28 分钟｜第一次切分：先看任务，再看共同分母

### 3.1 六步切分法

讲师逐步板书，每步用星桥商城举例：

1. **列守恒表**：给 A01–A40 编号，每个 API 必须恰好归属一个工具。
2. **按用户任务聚类**：了解客户、发现商品、结算试算、查询订单、处理支付、追踪履约、处理工单。
3. **区分只读与写入**：查询支付和扣款不是同一种能力。
4. **检查权限与确认**：报价可以低交互，下单、取消、退款必须明确批准。
5. **检查一致性与失败**：四项报价是否必须同一份快照？写超时后有没有查询事实的工具？
6. **检查模型交互成本**：工具是否一句话讲得清？条件字段是否太多？输出是否过宽？

### 3.2 小组练习（7 分钟）

只看资料包第 2 节 A01–A22，不翻后面的 16 工具答案。每组完成：

- 把这 22 个 API 归成若干工具；
- 给每个工具写一句不含“和/或/等等”的用途；
- 圈出所有敏感写；
- 标出至少一处“虽然能合并，但不应该合并”。

**质疑者追问模板**：

```text
如果把这两个动作放在一个 Registry 条目里：
1. 它们是否需要相同确认？
2. 它们是否能使用相同重试策略？
3. 一次超时后，查询哪一个事实？
4. 模型会不会因为动作太多而填错条件字段？
```

### 3.3 收束点评（3 分钟）

不要求各组数字相同。选两种常见方案对比：

- **按 REST 资源聚合**：`customer_api/product_api/order_api/payment_api`；优点是名称少，缺点是读写与权限混在一起。
- **按端点拆分**：容易校验局部参数，但简单查询也要模型连续选择多次，描述和误选成本上升。

讲师总结：

> 合并看内聚，拆分看边界。读操作更常按上下文聚合；写操作更常按承诺点和授权边界拆分。最后还要回到当前 Registry 的条目级策略，检查合并后的共同分母。

## 4. 28–42 分钟｜公布答案：为什么是这 16 个

### 4.1 完整地图

| # | 工具 | API 数 | 一句话边界 |
| --- | --- | ---: | --- |
| 1 | `get_customer_context` | 4 | 读取同一客户的资料、地址、会员和偏好 |
| 2 | `explore_catalog` | 4 | 用封闭模式完成商品搜索、详情、规格和库存发现 |
| 3 | `quote_checkout` | 4 | 对同一购物车 revision 生成一致报价，不下单、不扣款 |
| 4 | `get_cart` | 1 | 读取一个高频、独立的购物车快照 |
| 5 | `update_cart` | 4 | 创建或修改购物车，共享 revision 冲突语义 |
| 6 | `create_order` | 1 | 把指定报价转成订单这一独立承诺点 |
| 7 | `query_orders` | 3 | 查询订单列表、详情或时间线 |
| 8 | `cancel_order` | 1 | 在明确状态下取消指定订单 |
| 9 | `manage_payment` | 2 | 在支付状态机内执行授权或扣款 |
| 10 | `get_payment_status` | 2 | 按支付或订单核对支付事实 |
| 11 | `inspect_refund` | 2 | 按退款或支付查询退款事实 |
| 12 | `request_refund` | 1 | 提交一次有独立资金副作用的退款请求 |
| 13 | `query_shipments` | 3 | 查询运单、订单运单或轨迹 |
| 14 | `change_delivery` | 2 | 修改收货地址或改派站点 |
| 15 | `query_support_cases` | 2 | 查询客服工单列表或详情 |
| 16 | `manage_support_cases` | 4 | 创建、回复、关闭或重开工单 |

让学员口算：`4+4+4+1+4+1+3+1+2+2+2+1+3+2+2+4=40`。守恒检查能防止“合并以后忘了某个端点”，但不能单独证明粒度合理。

### 4.2 三类合并理由

**第一，读上下文内聚。**
A01–A04 都是同一客户的只读信息，所以用 `include` 选择需要部分，而不是让模型为“这个客户是谁”做四次低价值选择。若地址权限以后独立，就应重新拆分。

**第二，一致性快照内聚。**
A09–A12 的商品价格、配送、优惠和税费必须落在同一 cart revision 和同一过期时间下。这里合并不是为了少几个工具，而是防止模型把不同报价片段拼成一个看似精确、实际无效的总额。

**第三，状态机内聚。**
支付授权与扣款、运单改址与改派、工单创建与状态变更分别共享业务状态和 revision。合并后必须记录策略代价，不能假装每个 action 都能独立配置。

### 4.3 三类拆分理由

- **查询与资金写分开**：`get_payment_status` 与 `manage_payment`、`inspect_refund` 与 `request_refund`。
- **承诺点独立**：报价不是下单，下单不是支付，取消订单也不自动等于退款。
- **高频简单调用独立**：`get_cart` 只有一个必要参数，没有必要让模型先选择 action。

### 4.4 明确记录的不完美

讲师指着工单工具说：

> `manage_support_cases` 把 create、reply、close、reopen 放在一起，共享工单状态机；但当前 sensitive 是条目级，所以创建和回复也必须逐次确认。这是本方案有意接受的保守成本，不是最优雅的唯一解。如果确认疲劳真实发生，就拆成创建/回复与状态变更工具，或重新评估动作风险；绝不能声称 Registry 已经支持按 action 确认。

## 5. 42–56 分钟｜写入治理：确认、幂等、重试与未知结果

### 5.1 先建立四条规则

1. **sensitive 不等于有副作用**：更新购物车是普通写但非敏感；下单、支付、退款等是本方案的敏感写。敏感分级需由业务风险决定。
2. **确认绑定本次参数**：确认界面展示动作、对象、金额、币种和 requestId；不是“以后都允许”。
3. **幂等是实现出来的**：在 Schema 里放一个 requestId，不会自动产生持久去重。
4. **超时是结果未知**：网络超时不能推出“服务端没执行”，尤其不能推出“可以重新扣款”。

### 5.2 课堂推演 A：从报价到下单（非真实执行）

> 以下参数、ID 和结果都是讲师用于推演的虚构样本，不是终端实录，也不是商城适配器的测试输出。

用户：“就按刚才 259 元的报价下单，选标准配送。”

讲师展示：

```json
{
  "requestId": "req-order-demo-001",
  "quoteId": "quote-demo-001",
  "shippingOptionId": "standard",
  "acceptedTotalMinor": 25900,
  "currency": "CNY"
}
```

提问：“确认框只写‘允许 create_order’够不够？”

**答案**：不够。必须展示 quoteId、配送选项、25900 最小货币单位对应的 259.00 元、CNY 和本次请求标识。批准只覆盖这次 callId 和参数，不覆盖未来的取消、支付或另一份报价。

成功输出的业务含义是 `status=pending_payment`，讲师必须说“订单已创建，等待支付”，不能说“购买成功且已扣款”。

### 5.3 课堂推演 B：扣款超时（非真实执行）

前置事实：订单 `order-demo-001` 已创建，用户另行明确批准扣款 259.00 元。

**第一步：发起一次逻辑调用。**

```text
manage_payment(action=capture, paymentId=pay-demo-001,
               amountMinor=25900, currency=CNY)
→ 参数校验通过
→ 本次敏感确认通过
→ 本次尝试超过教学示例预算
→ 返回 TOOL_TIMEOUT（结果未知）
```

强调：敏感确认每次逻辑 `registry.execute` 一次，不是每次内部重试一次；本工具安全基线是 `maxRetries:0`，所以这里不会自动再扣一次。

**第二步：回喂并改变下一步，而不是盲目重试。**

```text
TOOL_TIMEOUT
→ get_payment_status(mode=by_payment, paymentId=pay-demo-001)
```

两种虚构分支：

| 查询事实 | 下一步 | 禁止的结论 |
| --- | --- | --- |
| `captured` | 告知已扣款，停止重复 capture | 因第一次超时就再次扣款 |
| 暂时 `RESOURCE_NOT_FOUND` 或查询依赖不可用 | 保留未知状态，稍后对账或人工处理 | 断言一定没扣款 |

讲师总结板书：

```text
写超时 ≠ 写失败 ≠ 未执行
正确链路：确认 → 执行 → 超时回喂 → 查询事实 → 再决定
```

### 5.4 重试共同分母

`update_cart` 包含创建、设置数量、删除规格和优惠码。后几种可在相同 revision 下设计成幂等，创建却依赖 requestId 持久去重。当前条目策略不能按 action 改变，所以统一 `maxRetries:0`。

问：“什么时候值得拆出 `create_cart`？”

**参考答案**：创建调用频繁、去重已可靠、其他更新确实有自动重试价值，并且新增工具带来的发现成本低于统一不重试的代价。不是看到四个 action 就机械拆四个。

## 6. 56–66 分钟｜Schema 能挡什么，不能挡什么

### 6.1 当前真实支持范围

本课资料只用源码实际执行的子集：

- 类型：`object/string/number/integer/boolean/array/null`；
- 结构与约束：`properties/required/additionalProperties:false/items/minLength/minimum/maximum/enum`；
- 根输入必须是 object；数组与嵌套对象递归校验；错误定位到具体路径；
- 不自动 trim、强转、填默认值，也不会因为写了 Schema 就自动验证业务输出。

**源码核对差异**：ADR-001 的文字列表包含 `maxLength/uniqueItems`，但 D032 基线的 `src/tools/schema.ts` 实际未执行这两个关键字。本资料不依赖它们；字符串最大长度、数组长度与唯一性由业务层检查。发现文档与实现差异时，应以可运行证据为准并另行修正文档，而不是把未执行约束当安全防线。

也不支持 `$ref`、`oneOf/allOf`、`pattern`、`format` 或条件必填。下列“输出 Schema”是成功业务载荷的设计规格，当前 Registry 不会自动校验它。

### 6.2 三个样本由哪一层拒绝

以 `explore_catalog` 为例：

| 样本 | 结果 | 原因 |
| --- | --- | --- |
| `{ "mode":"search", "query":"键盘", "extra":true }` | Registry 拒绝 | 显式 `additionalProperties:false` |
| `{ "mode":"detail", "query":"键盘" }` | Registry 拒绝 | mode 不在封闭枚举内 |
| `{ "mode":"product" }` | Registry 可通过形状校验，业务层必须拒绝 | product 模式条件需要 productId，当前子集无法表达 |

讲师强调：

> “Schema 通过了”只说明一般形状符合，不说明业务请求合法。条件必填、资源归属、金额与授权一致、状态机和 revision 都由工具业务层继续校验。失败要返回可修复的路径和 hint，而不是笼统的“参数错误”。

### 6.3 输出与错误也要设计

成功输出应当小、稳定、可判别：列表为空是正常事实，`processing` 是正常状态，支付 `captured` 与退款 `requested` 不能被扩写成“已到账”。

失败统一走真实 `ToolResult` 的 `isError/error`，不能返回一个看似成功的 `success:false` 让运行时误判。Loop 回喂给模型的是序列化 content 与工具关联信息，不会自动把内部整个 error 对象或异常堆栈塞给模型；工具作者仍须保证 content 不含秘密和提示注入指令。

## 7. 66–75 分钟｜七个反例：为什么“能跑”还不够

每页先让学员指出风险，再显示修正。

### 反例 1：40 API = 40 工具

**问题**：简单任务被迫做大量相似选择，描述 token 和测试矩阵膨胀。
**修正**：同上下文、同权限的只读查询按任务聚合，例如 `get_customer_context(include)`。

### 反例 2：一个万能 `commerce_api`

```json
{ "method":"任意字符串", "path":"任意字符串", "headers":{}, "body":{} }
```

**问题**：模型获得任意请求代理；权限、校验、错误和审计全部失去领域边界。
**修正**：封闭工具名与 action 枚举，逐工具 Schema，敏感写独立确认。

### 反例 3：一个 `manage_commerce` 管所有读写

**问题**：条目级权限与韧性只能取共同配置，不是人人确认，就是资金写被放宽。
**修正**：按副作用和授权边界拆分。

### 反例 4：把高级 Schema 当成现有能力

**问题**：写了 `oneOf/$ref` 也不代表 Registry 会执行；只写 action 又指望模型自然填对，同样不可靠。
**修正**：当前子集做第一层校验，业务层做条件校验并给出具体错误。

### 反例 5：所有错误都重试

**问题**：参数、权限、支付拒绝和状态冲突不会因重试变好；资金写重试可能重复副作用。
**修正**：确定性错误立即回喂；幂等读有限重试；写超时先查事实。限流和熔断不在同一逻辑调用中立即自动重试。

### 反例 6：让模型传 tenantId 并信任它

**问题**：模型参数是调用方数据，不是身份。
**修正**：可信 tenantId 由 Registry 策略写入 ToolContext，业务层仍验证资源归属。

### 反例 7：原始大报文或字符串包一切

**问题**：模型难以稳定引用字段，原始响应可能过大、泄密或带提示注入。
**修正**：有界、稳定的业务输出；失败走结构化 ToolResult；必要时分页和摘要。

## 9. 84–90 分钟｜总结与退出题

### 总结讲师稿

> 今天不是把 40 变成 16，而是把 40 个传输端点重新组织成 16 个可理解、可授权、可失败、可测试的任务边界。
>
> 读操作看上下文，写操作看承诺点；合并看内聚，拆分看权限和失败。Schema 是入口，不是业务正确性的全部；requestId 是设计，不是自动幂等；超时是未知，不是失败；能调用不等于应该合并。
>
> 最后请用资料包第 7 节的 16 条清单审查自己的答案。工具数量是结果，治理闭环才是交付。

### 退出题（2 分钟）

1. 为什么 `quote_checkout` 应该合并四项报价，而 `request_refund` 应该独立？
2. `manage_payment` 返回超时后，为什么下一步不是自动 capture？
3. `explore_catalog(mode="product")` 没带 productId，为什么仅靠当前 Registry Schema 不够？

**标准答案**：

1. 四项报价需要同一 cart revision 与过期时间，是无订单、无扣款的一致性试算；退款是独立资金副作用，需要独立权限、逐次确认、幂等和写后查询。
2. 超时不代表未执行，自动重试可能重复扣款。基线 maxRetries 为 0，应先查支付事实；查不到也不能立即断言未扣款。
3. 当前子集不能表达 mode 与 productId 的条件必填关系；Registry 只校验一般形状，业务层必须继续校验并返回可修复错误。

## 10. 课后练习与完整答案

以下练习均可直接用资料包作答。先独立完成，再对照答案；答案不是唯一命名，但必须保持业务与治理语义。

### 练习 1：映射守恒审查

某同学提出 15 个工具：把 `get_cart` 合并进 `update_cart`，其他 15 个不变。是否一定更好？需要检查什么？

**参考答案**：不一定。API 仍可做到 40 个无遗漏，但合并会让只读购物车快照与创建/修改共享条目。需要检查只读调用者是否因此获得写工具发现、普通写策略是否影响高频查询、action 是否增加、重试共同分母是否迫使读取也不能重试。D033 选择独立 `get_cart`，因为高频、参数简单、只读权限清晰；如果实际调用证据显示独立工具收益消失，可以再评审，而非凭数量判断。

### 练习 2：支付工具的条件参数

为 `manage_payment(action=authorize)` 和 `capture` 分别列出必要业务字段，并说明为什么 Schema 只把 action、requestId、amountMinor、currency 设为共同 required。

**参考答案**：authorize 还需要 orderId 与 paymentMethodId；capture 还需要 paymentId。金额与币种必须和订单/授权事实一致。当前 Schema 子集无法按 action 表达不同 required，所以共同字段放 Registry Schema，模式特有字段由业务层校验；不适用字段应省略，避免拿 orderId 冒充 capture 的充分条件。支付工具不得接收卡号或 CVV。

### 练习 3：工单拆分的完整方案

给出题目 A 的一种可行答案。

**参考答案**：可拆为 `create_support_case`（A37）、`reply_support_case`（A38）、`change_support_case_state`（A39–A40）。是否把前两者标 sensitive 要由业务风险决定；若认定为普通写，可在宿主仍保留 UX 提示，但不能伪称 Registry 自动按 action 判断。三者均保留租户/白名单与资源归属；回复和状态变更需要 caseId、适用时 expectedRevision；所有写操作的 requestId 由适配器持久去重，基线 maxRetries=0，超时用 `query_support_cases` 查事实。代价是工具数从 16 增至 18、发现描述增加，收益是确认策略可独立，且关闭/重开的状态机仍保持内聚。若建单也对外产生通知，仍可能需要确认，不能为了少点一次而隐瞒副作用。

### 练习 4：取消订单是否自动退款

设计“用户取消一笔已扣款订单”的工具链，并指出两次确认为什么不能合并。

**参考答案**：先 `query_orders` 获取订单与 revision，再经本次明确确认调用 `cancel_order`；取消成功后分别用 `get_payment_status`、`inspect_refund` 核对可退事实；如需退款，再以独立 requestId、paymentId、金额、币种和原因，经另一次明确确认调用 `request_refund`；最后用 `inspect_refund` 查询处理状态。取消与退款是不同对象、不同状态机和不同资金副作用，取消成功不保证退款可执行，退款请求被接受也不等于到账，所以不能用一次模糊批准覆盖两个承诺点。

### 练习 5：错误分类

把下列情况分成“可修正后重新调用”“换允许路径”“先查询事实”“停止或人工处理”：缺少 productId、TOOL_NOT_ALLOWED、RESOURCE_CONFLICT、支付 TOOL_TIMEOUT、PAYMENT_DECLINED。

**参考答案**：缺 productId 属于可修正参数后重新调用；TOOL_NOT_ALLOWED 换当前允许的工具或请求宿主授权，不能重试绕过；RESOURCE_CONFLICT 先重新读取 revision/status，再由用户决定，不能原样重放；支付 TOOL_TIMEOUT 先 `get_payment_status`，必要时对账；PAYMENT_DECLINED 停止自动重试，由用户换支付方式或终止。任何分支都受 Loop 连续错误上限约束。

### 练习 6：设计一个新工具前的完整审查

请用不超过 16 条，写出可复用的粒度清单。

**参考答案**：采用资料包第 7 节：一句话意图、业务内聚、调用频率、读写分离、权限一致、副作用可解释、输入可判别、输出有界、幂等可证明、重试共同分母、失败可恢复、每尝试超时预算、独立可测、模型可发现、演化信号、映射守恒。仅写“高内聚低耦合”不够，因为无法指导 Registry 配置、业务校验和失败测试。

## 11. FAQ：讲师可直接使用的回答

### Q1：16 是不是比 40 更好，所以越少越好？

不是。过少会把权限和失败语义揉在一起，过多会增加误选和描述成本。16 是本案例的取舍结果；清单中的拆分信号比数字本身重要。

### Q2：为什么 REST 资源不能直接当工具？

资源可以作为聚类线索，但同一资源常有查询和敏感写，不同资源又可能属于同一一致性快照。工具要对齐任务与治理，而不是复制 URI 层级。

### Q3：GET 是否都能合并，POST 是否都要确认？

否。HTTP 方法不是完整业务风险模型。GET 可能返回不同密级的数据，POST 也可能只是无副作用试算。要看数据权限、实际副作用、可恢复性和产品风险分级。

### Q4：一个工具里有多个 action，是不是万能工具？

不必然。封闭枚举、同一对象/状态机、相同权限与可解释输出可以形成内聚领域工具；接受任意 method/path/body，或混合无关读写，才是万能代理风险。

### Q5：requestId 已经必填，为什么写工具还不自动重试？

因为字段存在不等于服务端或适配器实现了持久去重。跨进程、跨重启的同键去重需要真实存储与原子语义；未证明前，基线保持 maxRetries=0。

### Q6：retryable=true 是否就应该自动重试？

不是。还要满足工具注册的幂等许可、错误不在禁止重试集合，并受 maxRetries 限制。限流与熔断虽可提示稍后重试，但当前执行器不在同一逻辑调用中立即自动重试。

### Q7：每次尝试 5 秒、重试 2 次，总共就是 15 秒吗？

不能这样承诺。当前没有独立总 deadline；排队、退避和每次尝试的执行时间都会影响总耗时，外部取消则可提前终止。5 秒等数值在本课只是教学建议，不是实测 SLO。

### Q8：敏感工具每一次尝试都要重新确认吗？

不是。当前真实语义是每次逻辑 `registry.execute` 确认一次；若显式允许内部重试，同一批准覆盖这些尝试。因此敏感非幂等工具应保持默认不重试，除非另行评审。

### Q9：为什么不让模型直接传 tenantId，方便多租户？

模型参数不可信。Registry 根据策略写入可信 tenantId，并覆盖调用方上下文；业务层仍需检查 orderId、paymentId 等资源是否属于该租户。

### Q10：输出 Schema 会自动防止商城适配器返回错字段吗？

不会。本资料中的输出 Schema 是成功业务载荷设计；当前 Registry 校验输入，不按这些输出 Schema 校验业务返回。适配器必须自行测试输出，并限制敏感字段与大小。

### Q11：本课是否证明真实模型能使用这 16 个工具完成购物？

没有。本课没有注册或连接这些业务工具，课堂流程是推演。D032 的真实 Loop 使用离线脚本化 Provider 串联另一组 10 个工具，证明的是 Harness 链路，不是真实模型在本案例中的规划质量。

### Q12：有公开课视频或学员反馈吗？

没有。当前交付是讲义与资料包，课程尚未实际举办，无回放、无现场反馈。后续若真实授课，应另行记录实际日期、问题和改进，不能倒填为本次已经发生的成果。
