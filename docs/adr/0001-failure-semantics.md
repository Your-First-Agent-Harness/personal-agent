# ADR-001：工具设计取舍

- **状态**：Accepted（D031 定稿）
- **课程日期**：2026-12-11（D031 计划日期，不代表另行发布日期）
- **初稿来源**：D017《失败语义边界：哪些错误回喂、哪些错误终止》
- **决策者**：Stark
- **代码证据基线**：D030 `6a59ec10cd2a23b4d08c42359f81184971e11e0f`

> 本文件保留 D017 已接受的失败语义决策，并在 D031 根据 D027–D030 的真实实现扩展为完整的工具设计取舍。后文的注册、校验、权限和韧性决策不属于 D017 的事后倒填；演进记录见文末。

## 1. 背景

Personal Agent 的工具不是“模型随意调用的函数”。同一次调用会穿过模型契约、进程内注册表、参数校验、调用方策略、确认回调、韧性策略和 Agent Loop。任何一层语义不清，都会把普通故障变成越权、重复副作用、无限等待或失控循环。

D017 已决定：可预期的工具失败应作为 `role="tool"` 消息回喂，模型、Loop 和外部取消则按各自边界终止。D027–D030 又实现了可替换的注册表、递归 Schema 校验、白名单/租户/逐次确认，以及超时、重试、限流和熔断。D031 因而需要回答两个新问题：

1. 这些机制为什么按当前顺序组合，而不是各自堆叠？
2. 每项能力明确不承诺什么，复查时如何验证？

本 ADR 只记录现有本地 Harness 的决策，不引入插件市场、远程租户控制面、分布式熔断或新版本发布。

## 2. 决策总览

采用一条可解释的调用管线：

```text
注册/替换：先校验 Tool + Schema + resilience 配置，再原子修改 Map
     │
每个 Agent turn：list() 重新发现，单次模型请求保留该次 Schema 快照
     │
execute：可见性查找 → JSON 解析 → 递归参数校验 → 敏感调用逐次确认
     │
     └→ 熔断预检 → 有界并发/排队 → 再查熔断 → 每次尝试超时 → 有条件下重试
     │
     └→ 统一 ToolResult → 序列化 content 回喂 → 连续失败保险丝 / 正常完成
```

核心取舍是：**在真正执行前尽早拒绝，在执行后统一故障语义；把安全策略与韧性策略分开，但让二者共享同一个 Registry 条目生命周期。**

## 3. 已采用的决策、备选方案与 trade-off

### 3.1 工具契约、注册、发现与版本

#### 决策

1. `Tool` 同时持有 `name`、`description`、`parameters` 和 `execute`，避免模型看到的 Schema 与实际执行函数分离漂移。
2. Registry 以工具名为唯一键；`register` 拒绝重复名，`replace` 只允许替换已存在名称，`unregister` 立即移除后续发现与执行能力。
3. 注册选项支持非空 `version` 字符串、可遍历的 `metadata` 对象、权限与韧性配置。未声明版本显示为 `unversioned`，不隐式编造 `1.0.0`。
4. `discover()` / `describe()` 暴露名称、描述、Schema、版本和元数据；`list()` 只给模型名称、描述和 Schema，不把内部版本、租户或权限策略塞进模型契约。
5. 每轮 Agent 请求重新 `list()`；一次请求内部使用同一批 Schema。替换或注销影响下一轮发现，不 retroactively 改写已经发出的请求。
6. 新条目的 Tool、Schema 和 resilience 配置全部验证成功后才修改 Map；非法替换保留旧条目。
7. 执行开始时捕获当前条目。执行期间的替换或注销不会强杀该次已开始的调用，新调用使用新状态。

#### 备选方案

- **静态工具数组**：实现更简单，但不能按轮替换、注销或做条目级治理。
- **Schema 与 execute 分开注册**：便于远端生成描述，却容易出现“说明已升级、执行仍停留在旧版”。
- **`name@version` 多版本共存**：适合兼容协商和灰度，但需要版本选择、依赖解析和调用协议改造。
- **整个 run 只快照一次**：请求更稳定，但运行期间无法撤销有问题的工具或让修复版生效。
- **执行中也强制切换/取消**：可减少旧代码残留，却会中断已开始的副作用，需要额外取消协议。

#### Trade-off 与后果

- 单名单活动条目让模型契约和策略都简单，但**版本目前只是诊断元数据**：不强制 SemVer、不比较大小、不做兼容协商，也不能同时注册两个版本。
- 按轮刷新兼顾可撤销性与请求内稳定性，代价是一次长 run 的不同轮可能看到不同工具集合。
- 替换会建立新的执行器和空韧性状态；旧调用的限流、连续失败计数不会迁移到新版本。
- Registry 是进程内目录，不是远程插件仓库。Map 以名称为键，也意味着不同租户不能各自注册同名但不同实现的条目。
- 当前未深冻结工具、Schema 或 metadata 对象；可信代码不应在注册后原地修改它们。该机制不是防御恶意进程内代码的沙箱。

**复查依据**：`src/core/tool.ts`、`src/tools/registry.ts`、`src/runtime/loop.ts`；`test/d027-tool-registry.test.ts` 覆盖版本发现、旧式注册、原子替换、非法注册和注销，`test/d029-permissions.test.ts` 覆盖按策略过滤后的发现。

### 3.2 递归 Schema 校验

#### 决策

1. 注册时递归检查 Schema 自身的形状，根参数必须为 `type: "object"`；非法注册或替换直接抛 `TypeError`，不留下半注册条目。
2. 执行前递归验证 JSON 值。当前支持：
   - `object`、`string`、`number`、`integer`、`boolean`、`array`、`null`；
   - `properties`、`required`、`additionalProperties: false`、`items`；
   - `minLength` / `maxLength`、`minimum` / `maximum`、`enum`、`uniqueItems`。
3. 数组和嵌套对象使用同一路径规则，报告 `$.members[1].name` 这类具体位置、期望值和修复提示。
4. 校验失败返回 `INVALID_ARGUMENTS`，工具 `execute` 与敏感确认回调都不运行；合法参数保持原值，不自动 trim、类型强转、填默认值或删除未声明字段。
5. 未声明字段默认允许，只有对象显式设置 `additionalProperties: false` 才拒绝。

#### 备选方案

- **信任模型参数**：代码最少，但坏参数会进入文件、命令或网络副作用。
- **每个工具手写校验**：可贴合业务，却会重复且错误格式不一致。
- **直接引入完整 JSON Schema 校验器**：标准覆盖更广，但增加依赖、配置和模型提供商兼容矩阵。
- **自动纠错/强转**：调用更宽松，但会把模型错误变成隐蔽的不同操作，尤其不适合路径、数值和权限参数。

#### Trade-off 与后果

- 自建子集保持零新增依赖、错误路径可读，且与现有内置工具一致；代价是维护者必须清楚支持范围。
- 这不是完整 JSON Schema：未实现 `$ref`、`oneOf` / `allOf`、`pattern`、`format` 等语义，也不保证任意合法 Schema 都被模型提供商接受。不要把未实现关键字当作安全约束。
- 严格校验把修复责任交还模型/调用方，但错误参数仍可能反复出现，因此必须由 Loop 的连续失败上限兜底。
- `integer` 接受所有有限整数，不限于安全整数；超大整数精度与更深层业务不变量仍需工具自身处理。

**复查依据**：`src/tools/schema.ts`、`src/tools/registry.ts`；`test/d028-schema-validation.test.ts` 覆盖 35 个测试，包括嵌套数组路径、约束边界、非法 Schema、替换回滚和内置工具注册。

### 3.3 白名单、租户与敏感工具逐次确认

#### 决策

1. **白名单**：未配置 `allowedTools` 表示不额外限制；配置空数组表示全部禁止。被禁止工具不可发现，执行时统一返回 `TOOL_NOT_ALLOWED`。
2. **租户**：共享工具对当前策略可见；租户专属工具只对 Registry 配置的同租户调用可见。未配置租户时不默认开放任何租户专属工具。
3. **可信上下文**：只有可见条目的 Registry 策略能写入 `ToolContext.tenantId`；调用方传入的其他租户值会被覆盖，隐藏条目更不会借伪造上下文执行。
4. **逐次确认**：注册为 `sensitive: true` 的工具，每次逻辑 `registry.execute` 都必须取得本次明确批准。批准内容包含 `callId`、工具名、已解析且校验通过的参数和可信租户；不保存“永远允许”。
5. 未配置确认回调或回调拒绝均返回 `TOOL_CONFIRMATION_REQUIRED`；回调抛错统一为脱敏的 `TOOL_CONFIRMATION_FAILED`，不执行工具。
6. 顺序固定为：先检查可见性，再解析 JSON 和校验参数，最后请求确认。隐藏工具不会通过错误差异泄露 Schema；无效参数不会触发无意义的人工确认。

#### 备选方案

- **只在启动时授予能力**：运行更快，但撤销和单次高风险授权不灵活。
- **只隐藏模型 Schema、不检查 execute**：能减少误调用，却无法防御伪造 ToolCall。
- **信任调用方 tenantId**：接入简单，但可直接冒充其他租户。
- **一次批准、整个会话有效**：交互更少，但批准会错误覆盖不同参数和后续副作用。
- **先确认再校验**：看似更安全，实际会让人审批畸形或无法理解的请求。

#### Trade-off 与后果

- 发现与执行使用同一可见性谓词，降低“模型看不到但直接调用却能成功”的缝隙；统一拒绝也减少了隐藏条目的信息泄露。
- 每次确认增加交互成本，但把批准绑定到具体参数，适合敏感写操作。
- **逐次是每次逻辑调用一次，不是每次内部重试一次**。若敏感工具显式启用自动重试，同一批准覆盖该次调用的所有尝试；敏感非幂等工具应保持默认不重试，除非明确接受风险。
- 这是进程内策略，不是完整 IAM：没有持久授权、审计存储、身份认证、跨进程租户目录或加密隔离。确认回调收到原始参数，宿主 UI 和日志仍需自行保护敏感信息。

**复查依据**：`src/tools/registry.ts`、`src/core/tool.ts`；`test/d029-permissions.test.ts` 覆盖白名单、租户 spoofing、逐次批准/拒绝、确认异常脱敏、校验顺序和权限错误回喂。

### 3.4 每次尝试超时、幂等重试、有界排队限流与 half-open 熔断

#### 决策

##### 每次尝试超时与取消

- `timeoutMs` 对每一次工具尝试单独计时，而不是把全部重试共用一个计时器。
- 每次尝试创建子 `AbortController`；外部 `AbortSignal` 优先，超时也会中止该次 signal。
- Promise 只接受第一次 settle；超时后的迟到成功/失败不会改变已返回结果，迟到 rejection 会被消费。
- 未配置 resilience 时走直接执行路径，保留 D029 的 context signal 身份和原结果对象，避免无谓行为变化。

##### 幂等重试

- `maxRetries` 默认 `0`。只有 `retry.idempotent: true`，或明确 `allowNonIdempotent: true`，才允许自动重试。
- 仅重试 `isError: true`、`error.retryable: true` 且不在禁止重试集合中的故障；退避为 `baseDelayMs * 2 ** attempt`，等待也可被外部取消。
- `TOOL_RATE_LIMITED` 和 `TOOL_CIRCUIT_OPEN` 虽提示调用方可稍后重试，但不进入当前执行器的立即自动重试，避免刚被拒绝就放大压力。
- 参数、JSON、权限、确认、取消和路径越界等确定性/策略错误不自动重试，也不计入熔断。

##### 有界排队限流

- 同一 Registry 条目限制逻辑调用并发 `maxConcurrent`；许可占满时，`maxQueue` 默认 `0`，即直接拒绝。
- 配置队列后仍受 `maxQueue` 和 `maxWaitMs` 双重约束；队列 FIFO，取消或超时等待会移除排队者。
- 许可覆盖该逻辑调用的所有尝试和退避，直到最终结果才转移给下一个等待者。
- 在排队前做一次熔断预检，取得许可后再检查，避免冷却期拒绝或 half-open 规则被排队绕过。

##### half-open 熔断

- 连续可重试故障达到 `failureThreshold` 后打开；冷却期快速返回 `TOOL_CIRCUIT_OPEN`。
- 冷却结束只放一个 half-open 探针；探针成功关闭并重置计数，失败立即重开并重新计算冷却。
- 每个逻辑调用只计一次最终结果，内部多次重试不会一次烧断工具；closed 状态成功会清零连续失败。

#### 备选方案

- **只限制整个 Loop 的 turn 数**：能防逻辑死循环，不能阻止一个永不 settle 的工具调用。
- **所有失败立即重试**：实现简单，但会重复写入、重复确认压力并放大故障。
- **无限队列**：短期不拒绝请求，但会把过载转成不可控延迟和内存增长。
- **永久打开或全量并发探测**：前者无法自动恢复，后者会在恢复瞬间再次压垮依赖。
- **按尝试计数熔断**：统计直观，但一次逻辑调用的多次重试会异常加速打开熔断器。

#### Trade-off 与后果

- 每次尝试超时让重试预算可解释，但**没有独立的总耗时预算**；总耗时还受尝试次数、退避、排队和外部取消影响。
- AbortSignal 是协作式取消。通用 Registry 超时不能保证杀死无视 signal 的 Promise、子进程或远端工作，只保证 Harness 不再接受迟到结果。
- 持有许可执行退避能限制单个依赖的整体压力，但会增加队头等待；当前没有优先级、公平租户调度或 jitter。
- 限流与熔断状态按 Registry 条目隔离，替换后重置；没有跨 Registry、跨进程或跨实例共享状态。
- 熔断只统计明确可重试且非策略类的最终失败，能减少参数错误导致的误熔断，但也意味着某些 `retryable: false` 的真实依赖故障不会触发打开。
- 当前没有指标导出、Retry-After、幂等键、随机退避或分布式协调；这些不能被测试中的状态机通过所替代。

**复查依据**：`src/tools/resilience.ts`、`src/tools/registry.ts`；`test/d030-resilience.test.ts` 覆盖 40 个测试，包括迟到 rejection、退避取消、每尝试计时、队列移除、条目隔离、单探针、失败重开、逻辑调用计数和 Loop 回喂。

### 3.5 失败回喂与终止语义

#### 决策

1. 可预期工具失败返回 `ToolResult`：`content` 是可读消息加可选提示，`isError: true` 标记失败，`error` 提供 code/message/retryable/hint 给运行时判断。
2. Loop 回喂给模型的消息只序列化 `content`，同时保留 `toolCallId` 和工具名；不会自动把整个内部 `error` 对象或异常堆栈塞给模型。
3. 工具抛出的 `ToolError` 保留结构化语义；其他异常统一脱敏为 `INTERNAL_ERROR`，不暴露原始异常消息。
4. 工具失败本身不中断 Loop。成功结果清零连续失败计数，失败递增；达到 `maxConsecutiveToolErrors`（默认 3）后以 `tool_errors` 终止，模型没有义务无限自救。
5. 模型提供商故障仍向上抛出；模型取消、外部取消、`maxTurns` 和连续工具错误分别终止。工具失败与模型失败不混为一类。
6. 自动重试发生在 Registry 内，Loop 只看到最终逻辑结果；`retryable: true` 是“可重试”提示，不等于绕过幂等和禁止重试规则。

| 失败类别 | 回喂 | 自动重试 | 熔断计数 | 说明 |
| --- | --- | --- | --- | --- |
| `UNKNOWN_TOOL` / `INVALID_JSON` / `INVALID_ARGUMENTS` | 是 | 否 | 否 | 模型可修正名称或参数；连续错误保险丝仍生效 |
| `TOOL_NOT_ALLOWED` / 确认失败 | 是 | 否 | 否 | 不借重试绕过策略，隐藏工具不泄露 Schema |
| 路径越界、确定性业务/参数错误 | 是 | 否 | 否 | 修正输入或改走允许的操作 |
| 明确 `retryable: true` 的工具/命令故障 | 是 | 仅在幂等许可后 | 是 | 最终逻辑结果只计数一次 |
| `TOOL_TIMEOUT` | 是 | 仅在幂等许可后 | 是 | 每次尝试独立计时，迟到结果不覆盖 |
| `TOOL_RATE_LIMITED` / `TOOL_CIRCUIT_OPEN` | 是 | 当前执行器不立即重试 | 否 | 调用方/模型可稍后发起新的逻辑调用 |
| 外部取消 / 工具取消 | 按当前阶段返回或终止 | 否 | 否 | 不继续后续尝试 |
| 模型提供商异常 | 否，向上抛出 | 不属于工具重试 | 否 | 不伪造成工具结果 |

#### Trade-off 与后果

- 可读回喂让模型能修复输入、换工具或解释失败，但也把工具输出带入模型上下文；文件和命令内容仍可能包含提示注入或敏感数据，当前没有通用清洗/密文扫描器。
- 统一脱敏保护未知异常细节，但工具主动构造的 `ToolError.message` 和正常 `content` 仍由工具作者负责，不能包含秘密。
- 连续错误保险丝限制无效自救，却可能在长任务中因连续不同工具的失败而停止；这是有意的保守默认值，可由调用方配置。
- 错误回喂不是“所有失败都继续”：外部取消、模型故障和 Loop 保险丝仍有明确终止权。

**复查依据**：`src/tools/errors.ts`、`src/core/tool.ts`、`src/runtime/loop.ts`、`test/d004-tool-errors.test.ts`、`test/d029-permissions.test.ts`、`test/d030-resilience.test.ts`。

## 4. 工具设计检查项

新增、替换或审查工具时，按以下清单逐项回答；不能只检查 `execute` 是否返回成功。

### 契约与发现

- [ ] 名称、描述、根 object Schema 和 execute 是否同属一个 Tool，描述是否准确说明副作用？
- [ ] version 是否仅作非空诊断元数据？若留空，是否接受 `unversioned`，而非假设兼容？
- [ ] metadata 是否为可遍历对象，是否避免放入秘密或模型不需要的内部策略？
- [ ] register/replace/unregister 的可见性和下一轮发现是否符合预期？非法替换是否保留旧工具？
- [ ] 是否理解同名只能有一个活动条目、替换会清空该条目的韧性状态、进行中调用不会被强切？

### Schema 与参数

- [ ] Schema 是否只使用当前支持的类型和约束，根类型是否为 object？
- [ ] 嵌套对象/数组错误能否定位到完整路径？required、边界、additionalProperties 是否符合真实业务？
- [ ] 是否避免依赖未实现的 `$ref`、组合、pattern、format 或提供商一定支持？
- [ ] 是否接受“不自动纠错、不强转、不填默认值”？额外字段应允许还是显式拒绝？
- [ ] 业务不变量、安全整数精度、路径/命令副作用是否仍需工具自身校验？

### 权限与确认

- [ ] allowedTools 未配置与空数组的语义是否符合调用方意图？
- [ ] 共享/租户归属是否明确，是否由 Registry 而非调用参数决定可信 tenantId？
- [ ] 隐藏工具的发现与直接执行是否都拒绝，错误是否避免泄露 Schema 和秘密？
- [ ] sensitive 工具是否每次逻辑调用重新确认，确认前参数是否已校验？
- [ ] 回调缺失、拒绝、异常是否安全失败？UI/日志是否保护确认请求中的原始参数？
- [ ] 敏感非幂等工具是否保持不重试；若开启，是否明确同一批准覆盖所有内部尝试？

### 韧性

- [ ] timeoutMs 是每次尝试预算；工具是否真正响应 AbortSignal，是否能清理子进程/连接等资源？
- [ ] maxRetries 是否默认 0？幂等依据是否真实，allowNonIdempotent 是否有明确副作用依据？
- [ ] 是否只把可恢复故障标为 retryable，避免参数、权限、取消和拒绝被重试？
- [ ] maxConcurrent、maxQueue、maxWaitMs 是否都有界，是否接受重试退避期间持有许可？
- [ ] 熔断阈值和冷却是否按逻辑调用理解，half-open 单探针成功/失败路径是否验证？
- [ ] 是否知道超时不是总 deadline、无限等待仍须 signal 协作、状态不跨实例共享？

### 回喂与测试

- [ ] 成功/失败是否都返回 ToolResult，error code、retryable 和 hint 是否一致？
- [ ] 非 ToolError 是否脱敏；工具主动生成的 message/content 是否也不含秘密和异常堆栈？
- [ ] 模型收到的 content 是否足以修复，又不会把权限策略或敏感内部细节泄露？
- [ ] 是否验证工具失败后 Loop 能继续，以及连续失败达到上限会停止？
- [ ] 测试是否断言 execute/spawn/confirm 是否应运行、尝试次数、队列/探针状态和迟到结果，而不只检查快照？

## 5. 总体后果

### 收益

- 工具从“可被模型调用的函数”升级为可发现、可拒绝、可约束、可恢复、可回喂的执行边界。
- 同一 Registry 条目统一承载版本、权限和韧性，避免不同模块对“当前工具”理解不一致。
- 执行前失败、执行中取消、执行后故障分别有可读语义；Loop 不因单次工具故障失去全部上下文。
- 默认不重试、默认不排队、默认无 Registry 超时，保留旧调用路径；需要能力的调用方必须显式配置。

### 代价与遗留边界

- 自建 Schema 子集和韧性状态机需要持续测试，不能声称等同完整标准或生产级分布式治理。
- 多机制叠加增加理解成本：逻辑调用与尝试、每尝试超时与总耗时、每次确认与每次重试必须区分。
- 当前只验证进程内、单 Registry 行为；未覆盖真实模型选择策略、外部身份系统、生产并发、长时性能或跨实例一致性。
- 工具输出信任、人工确认 UI、持久审计、资源强杀、随机退避、总预算和指标仍是独立问题，不在 D031 偷渡实现。

## 7. 演进记录：保留 D017 初稿决策

### D017（课程日期 2026-11-27）

原文件题为《失败语义边界：哪些错误回喂、哪些错误终止》，状态已经为 Accepted。初稿接受以下边界：

| 错误类型 | 决策 | 理由 |
| --- | --- | --- |
| 未知工具名 | 回喂 | 模型可能拼错，应自我纠正 |
| JSON 解析失败 | 回喂 | 模型输出格式问题，可重试 |
| 参数 Schema 校验失败 | 回喂 | 告诉模型哪里错了，模型可修正 |
| 工具执行异常（文件不存在等） | 回喂 | 模型可换路径或换工具 |
| Loop 控制信号（maxTurns、连续错误） | **终止** | 防止无限循环 |
| 用户取消 | **终止** | 用户意图优先 |
| 模型 API 调用失败 | **终止**（向上抛出） | 不是工具问题，重试在 provider 层处理 |

初稿的原始 trade-off 仍然成立：失败回喂让模型自我纠正，但错误信息应足够又不泄露内部细节；`maxConsecutiveToolErrors` 是最后保险丝，默认连续 3 个工具错误即终止。初稿也刻意把 `validateArguments` 的具体签名留到 D028。
