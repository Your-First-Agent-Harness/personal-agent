# ADR-000：从零实现核心，而不是基于现有框架

- **状态**：Accepted
- **日期**：2026-11-12
- **决策者**：Stark

## 背景

100 天要交付一个可被人使用的 Agent Harness，同时要能讲清"为什么这么做"。候选路径有四条：

- A：在 LangChain / LlamaIndex 上做二次封装
- B：用 Vercel AI SDK 作为底层，补齐工具与上下文
- C：自研 core，只在模型调用、MCP、存储上使用官方 SDK
- D：fork 一个成熟开源 Harness（如 OpenHands / SWE-agent）改造

## 评估维度

| 维度 | A 二次封装 | B AI SDK 底层 | C 自研 core | D fork |
|---|---|---|---|---|
| 能讲清每一步 | 差（被抽象吞掉） | 中 | 好 | 中 |
| 实现成本 | 低 | 低 | 高 | 中 |
| 可替换性 | 差（框架锁定） | 中 | 好 | 差 |
| 上下文可控度 | 差 | 中 | 好 | 中 |
| 观测与评测 | 需外挂 | 需外挂 | 原生 | 需改造 |
| 教学价值 | 低 | 中 | 高 | 中 |

## 决策

选 **C**：自研 core 与 runtime，模型调用、MCP、SQLite/PG 使用官方或成熟 SDK。

理由：

1. 项目的核心产出是"可解释的 Harness"，A / D 会把最关键的控制流藏在别人的代码里，直播时无法逐行讲。
2. 上下文工程是这个项目的差异化，B 的抽象层会限制预算与压缩策略的表达。
3. 自研不等于自造轮子：凡是协议与外部系统交互（模型 API、MCP、数据库），一律用官方 SDK，避免在无价值的地方消耗时间。

## 后果

**正面**

- Loop、工具协议、上下文策略都是本项目的一等公民，可独立测试与替换。
- 每个决策都能对应一篇 ADR + 一期直播内容。

**负面**

- 前期没有"开箱即用"的演示效果，D25 之前只有 CLI。
- 需要自己处理重试、超时、状态恢复等"框架里已经有了"的问题。

**缓解**

- 用 G1–G5 关卡控制范围，宁可少一个功能，不可少一份文档。
- 每层先做最小实现，再按周替换，避免一次性设计过度。
