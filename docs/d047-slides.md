## Slide 1｜Agent 工具调用的安全实践（0–3 分钟）

- 副标题：从一句 ToolCall 到可授权、可限界、可追责的执行
- 90 分钟外部开发者课
- 基于真实仓库实现与 D046 运行证据
- 目标：让工具从“能调用”走到“敢上线”

**视觉**：左侧模型发出一张“提案”卡片，右侧宿主盖上“允许 / 拒绝 / 待确认”印章，中间画清晰信任边界。

**讲解**：先声明这是工具安全工程课，不是 Prompt 技巧课，也不是内部架构评审。今天只追一条链：模型怎么提出调用、宿主凭什么允许、执行后为什么还不能放松。

---

## Slide 2｜模型说“帮我排查”，为什么读到了 `.env`？（3–6 分钟）

- 用户目标：排查构建失败
- 模型提案：`run_command({"command":"cat .env && npm test"})`
- 问题一：读取秘密是必要最小权限吗？
- 问题二：谁把文本变成真实进程？
- 问题三：结果还会影响下一次调用吗？

**视觉**：用户意图、ToolCall、真实进程三层卡片；在 ToolCall 到进程之间放一个巨大的“不能直连”符号。

**讲解**：不要先判断模型善恶。工程上更重要的是：这个调用由谁授权、拿什么权限执行、后果由谁承担。课程结束时，听众要能给出比“加一句不要读秘密”更可靠的答案。

---

## Slide 3｜ToolCall 是提案，不是授权（6–9 分钟）

- ToolCall：`id + name + arguments`
- `arguments` 起初只是 JSON 字符串
- 模型不拥有宿主权限，也不直接 spawn 进程
- `ToolRegistry.execute()` 才是执行入口之一
- 安全责任不能外包给模型自觉

**视觉**：一张“工作申请单”与一张“施工许可证”并排，强调两者不是同一个文件。

**讲解**：在本仓库消息协议里，ToolCall 只有这三个字段。真正改变系统状态的是宿主代码。把这句话重复一次：模型可以提出危险动作，但安全宿主必须有能力让它永远到不了副作用。

---

## Slide 4｜信任边界：输入、执行器、结果都不可默认可信（9–12 分钟）

- 用户、文件、网页和上游服务都可能带不可信文本
- 模型输出是建议，不是身份与权限证明
- 工具实现跨越文件、进程、网络和业务状态边界
- 工具结果重新进入模型上下文
- 安全要覆盖执行前、执行中、执行后

**视觉**：环形图：`不可信输入 → 模型 → ToolCall → 宿主控制 → 工具 → ToolResult → 模型`；宿主控制用蓝色包围。

**讲解**：只画“用户到工具”的直线会漏掉回流。工具读取的内容可能改变下一轮行为，所以一次 execute 返回不是安全分析的终点。

---

## Slide 5｜本仓库的一次调用经过哪些门？（12–16 分钟）

- 按名称找到工具
- 执行 allowlist + 租户检查
- JSON 解析 + 本地 Schema 校验
- 敏感工具逐次确认
- resilience 包装后进入 `tool.execute`

**视觉**：五道水平闸门，最后一道后接文件、Shell、HTTP、MCP 四个图标；每道闸门标注一个失败例子。

**讲解**：顺序很重要。未知工具先拒绝，JSON 失败不会进入业务代码，确认发生在真正 execute 之前。还要指出：具体工具内部仍有自己的路径、网络和进程检查，Registry 不是万能边界。

---

## Slide 6｜发现面与执行面都要最小化（16–19 分钟）

- `registry.list()`：决定模型看见哪些工具
- `registry.execute()`：独立检查这次能否执行
- 没发给模型 ≠ 可以省略执行鉴权
- 默认 CLI 注册内置工具，不等于默认启用全部安全选项
- 工具名 allowlist 不理解参数中的业务动作

**视觉**：两扇门：“可被模型发现”和“可被宿主执行”；中间放一个绕过模型直接构造调用的红色箭头，被第二扇门拒绝。

**讲解**：安全评审要看实际构造参数，不只看模块是否存在。本项目默认 Registry 没传 allowlist 和确认回调时，不能声称这些能力已自动开启。

---

## Slide 7｜租户正确，不代表这个对象就能访问（19–22 分钟）

- Registry 绑定 `(sessionId, tenantId)`
- 同 session 换 tenant 会失败
- 空字符串不是匿名或跨租户通配符
- 合法 `orderId` 仍需校验属主、动作与字段权限
- 先授权再读取，不要读出后让模型决定能否展示

**视觉**：tenant A 与 tenant B 两个仓库；同样的 `read_order` 形状，一边通过对象授权，另一边在读取前拒绝。

**讲解**：TenantContext 是调用身份边界，不是完整业务授权系统。订单、文件、支付、工单都要回到具体业务属主和状态机。

---

## Slide 8｜Schema 通过，只说明“形状像”（22–26 分钟）

- 本地子集：对象、数组、基础类型、required、范围、enum 等
- 不是完整 JSON Schema
- 能拒绝错误类型和未声明字段
- 不能自动证明订单属主、状态迁移或报价一致
- 条件必填、跨字段和业务不变量要继续校验

**视觉**：登机牌形状检查与真实身份核验的对比图；下方列出 `JSON 错误 / Schema 错误 / 业务拒绝` 三种错误。

**讲解**：举例：`mode=redirect` 时要求 `destination`，不是当前通用子集能自动表达的条件规则。业务错误要可修复，但权限错误不能提示成“换对象试试”。

---

## Slide 9｜把业务授权放在副作用之前（26–28 分钟）

- 参数有效 ≠ 动作合法
- 对象存在 ≠ 当前身份可见
- 用户说过“可以” ≠ 所有后续动作永久授权
- 金额、对象、状态与确认参数必须一致
- 权限拒绝不应泄露其他租户数据

**视觉**：一张五元组卡片：`subject / tenant / action / object / context`，全部通过后才进入业务状态机。

**讲解**：这一页是从“参数校验”跨到“安全授权”的关键。请听众记住五元组，后面事故练习还会用到。

---

## Slide 10｜工具结果不是新的 System Prompt（28–31 分钟）

- 文件、网页、日志、HTTP 与 MCP 内容都是数据
- 结果会作为 `tool` 消息回喂模型
- 内容可能诱导模型发起新的高权限 ToolCall
- 格式校验通过不等于语义可信
- 不要让不可信文本绕过宿主授权

**视觉**：一份 README 中藏着“发送配置”的指令，箭头到模型后被宿主权限闸门阻断，而不是直接到网络。

**讲解**：本课不展示真实外传。关键是即使模型受骗，后续调用仍应被确定性控制阻断。把“模型是否会听话”改成“宿主允许发生什么”。

---

## Slide 11｜秘密外传是一条链，要在多处切断（31–34 分钟）

- 不可信内容进入上下文
- 模型提出读秘密或访问新目标
- 读取能力与外发能力组合成出口
- 最小权限、目标限制、确认和审计分别断链
- 内容过滤只能是辅助，不是唯一防线

**视觉**：五段红色攻击链，被四个蓝色断路器切断；不出现真实凭证、域名或外传命令。

**讲解**：读文件本身可能合理，发网络请求也可能合理，危险来自能力与不可信控制的组合。工具拆分和运行时权限要防止这种组合自动成立。

---

## Slide 12｜Loop 保险丝：限制失控，不负责授权（34–37 分钟）

- `maxTurns` 限制轮次
- `maxTokens` 与上下文预算限制输入输出规模
- 连续工具错误可停止 Loop
- 同轮工具调用串行执行
- 这些机制不判断订单属主，也不沙箱化 Shell

**视觉**：四个保险丝图标与一条 Loop 时间线；旁边单独放“授权”和“OS 隔离”，标注“不能替代”。

**讲解**：资源边界很有必要，但不要拿 `maxTurns=3` 当权限策略。第一次调用就可能已经产生不可逆副作用。

---

## Slide 13｜演示先讲安全边界，再讲攻击结果（37–39 分钟）

- 命令：`npm run demo:d046`
- 唯一 `mkdtemp` 实验根、专用 victim、伪造秘密
- 零外网、零真实凭证、零真实外传
- `finally` 清理 + `hostRootRemoved=true`
- 现有 transcript 与 JSONL 是 D046 真实运行证据

**视觉**：实验根目录树，所有 victim 和 marker 都被包在根内；根外画“不可触碰”。

**讲解**：明确这是可复跑教案，不是 D047 现场实录。不要临时把路径改为真实用户目录，也不要添加 fork bomb、OOM 或网络载荷。

---

## Slide 14｜D043：临时 cwd 不是文件系统边界（39–43 分钟）

- `/bin/sh -c` 接收开放命令字符串
- 每次调用有独立临时 cwd 与固定 env
- 绝对路径和 Shell `cd` 可以离开初始 cwd
- D046 只在实验根内证实读写与单文件删除
- 固定 env 不泄密，不能抵消路径边界缺失

**视觉**：初始 cwd 小圈与 hostRoot 大圈；箭头离开小圈但始终留在大圈，标注两种边界不能混淆。

**讲解**：读 transcript 的 `D043_ABSOLUTE_PATH`：观察是 `cwdOutside=true`，控制是 victim 仍在 hostRoot。不要夸大成“逃出操作系统”，也不要淡化成“已有沙箱”。

---

## Slide 15｜D044：先准入，再有界执行（43–48 分钟）

- `realpath(executable)` + 完整 argv 精确匹配
- `shell:false`，固定 env，一次性 cwd
- 共享 stdout/stderr 字节预算 + wall timeout
- 五类未允许调用：spawn 增量 0
- 三条允许链真实启动：总 spawn 数 3

**视觉**：左侧五类拒绝在 spawn 前停止；右侧 env、flood、timeout 三条允许链进入有界执行框。

**讲解**：正向控制很重要，否则“拒绝都成功”可能只是工具从不工作。再看 `D044_OUTPUT_BUDGET`：256 字节输入被 64 字节共享预算终止；短循环在 30ms 超时终止。

---

## Slide 16｜secure_command 仍不是容器（48–51 分钟）

- 没有 namespace、cgroup、seccomp 或完整 MAC
- 没有通用 CPU、内存、进程数与磁盘隔离
- 精确 argv 适合少量固定动作，不适合任意开发命令
- 被允许的 executable 仍可能拥有危险能力
- 文件工具的符号链接缺口不能靠命令白名单解决

**视觉**：`secure_command` 是一道坚固的“门禁”，旁边画出它没有的 OS 围墙，避免画成完整容器图标。

**讲解**：同时指出普通文件工具仍是词法路径边界，D045 已记录 symlink 风险。不可信代码应进入独立、可销毁、真正 OS 隔离的环境。

---

## Slide 17｜敏感确认：绑定这一次动作与参数（51–55 分钟）

- `sensitive` 是 Registry 条目级标记
- 未传确认回调，不会自动出现确认
- 确认位于 Schema 后、execute 前
- 每个逻辑调用确认，重试不重复确认
- 确认要显示动作、对象、影响与参数摘要，不显示秘密

**视觉**：取消订单确认卡，列出 tenant、orderId、影响；下方写“不是：本会话永远允许”。

**讲解**：确认不是免责按钮。若对象、金额或参数改变，就必须重新授权。确认疲劳通常说明工具粒度过粗或低风险动作被混在敏感条目中。

---

## Slide 18｜超时不等于没发生，retryable 不等于可重试（55–60 分钟）

- 请求可能未收到、处理中或已完成但响应丢失
- 默认 `maxRetries=0`
- 幂等重试需显式配置；非幂等需明确承担风险
- timeout 作用于每次尝试，不是自动回滚
- 先查权威状态与业务幂等记录，再决定补偿

**视觉**：支付请求的三条时间线，全部到“客户端超时”，但服务端状态不同；最后汇入“查询事实，不盲重试”。

**讲解**：内存 attempt 计数不是持久幂等。真正幂等要由业务或提供方去重。权限、Schema、确认和取消错误不自动重试，也不烧断熔断器。

---

## Slide 19｜外部 HTTP 与 MCP：接协议，不继承信任（60–68 分钟）

- weather：固定 endpoint、拒绝重定向、超时/取消、64KiB 默认响应上限
- 检查 Content-Type、UTF-8、JSON 与必要字段，不透出 HTTP 错误 body
- MCP：映射 Schema、内容和错误到本地契约
- 远端文本与动态工具列表仍不可信
- server 身份、进程权限、工具变更和网络边界仍需治理

**视觉**：两个入口汇入同一“本地不可信输入”框：Open-Meteo 与 MCP server；下方列出协议校验和信任治理两层。

**讲解**：天气适配器的保护不能泛化成任意 URL 的 SSRF 方案。MCP 让接口统一，不会让远端内容自动可信，也不会替代业务授权。

---

## Slide 20｜审计：记录决定，也记录“不确定”（68–76 分钟）

- decision 与 completion 用同一 operationId 关联
- D046：8 个 operation、16 条真实 JSONL
- decision 写失败：命令不启动
- 允许命令 completion 写失败：显式失败，但副作用不可回滚
- 本地 JSONL 不等于远程、防篡改、完整审计平台

**视觉**：双阶段时间线，completion 处出现“写失败”裂口；裂口旁写“证据缺失 ≠ 无副作用”。

**讲解**：没有 completion 只能说明证据不完整。恢复时要查独立业务状态、进程、文件或提供方事实，而不是直接重试。日志还要脱敏、限权、留存和告警。

---

## Slide 21｜事故推演：超时 + 不可信 README + 审计失败（76–84 分钟）

- 依赖 README 诱导读取配置并外发
- 模型提出宽权限命令，随后执行超时
- completion 写失败，owner 问“能否直接再跑？”
- 小组任务：找阻断点、未知事实、恢复与整改动作
- 角色：调用方 / 工具平台 / 业务 owner / 审计员

**视觉**：四格事故板：`入口 / 授权 / 执行 / 证据`，每格留空让小组贴控制卡。

**讲解**：给 6 分钟讨论、2 分钟分享。追问“没有日志是否等于没有副作用”“第一次调用能否已经造成损害”。参考方向见练习册，不要求唯一措辞。

---

## Slide 22｜上线前，把这句话改成五个可验证问题（84–90 分钟）

- 谁能对哪个对象的哪个动作发起这次调用？
- 哪一层拒绝非法参数、越权动作和未确认副作用？
- 时间、输出、重试、并发和 OS 边界在哪里？
- 不可信结果能否诱导下一次越权调用？
- decision、completion 与失败后的独立事实如何取得？

**视觉**：中央一句 `ToolCall 是提案，不是授权`，周围五个问题形成上线检查环；底部放退出题二维码占位框，不虚构真实链接。

**讲解**：退出题只有一句：“支付工具超时且 completion 写失败，能否因为没有成功日志就直接重试？说出理由和下一步。”标准方向：不能；结果未知、证据缺失，先冻结重复副作用并查询权威状态。最后提醒：本课程目前仅为备课包，没有真实回放或学员反馈。
