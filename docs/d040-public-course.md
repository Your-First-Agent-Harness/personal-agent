## 0. 讲师一页速览

### 0.1 课程定位

- **核心问题**：MCP 正在成为开放标准，还是 Agent 工具集成演进中的一次过渡方案？
- **课程答案**：这不是二选一。MCP 已具备公开版本化规范、多实现、公开治理与一致性工作等开放标准的重要特征；但对具体团队，它仍可能因版本演进、传输与会话成本、Schema 适配、安全治理和生态质量差异而成为暂时边界。判断必须落到工作负载和可验证条件。
- **不适用方式**：把“很多厂商宣布支持”直接等同于全面互操作；把仓库 Demo 等同于行业调查；把本课当成技术投资或采购的绝对建议。
- **与 D033 的区别**：D033 讨论 API 如何划成 Agent 工具；本课讨论这些工具与外部系统之间应采用什么协议，以及这个边界能否长期保留。

### 0.2 学习目标

学员完成课程和练习后，应能：

1. 用**规范、SDK/实现、Server 生态、企业采用、实际互操作**五层证据审查“MCP 已是标准”这句话；
2. 画出模型私有 function calling、MCP、REST/OpenAPI 与 A2A 的不同边界，并说明它们为何可以共存；
3. 解释 2025-11-25 的初始化、能力协商、stdio 与 Streamable HTTP，并识别 2026-07-28 版本演进带来的兼容问题；
4. 说明为什么“名字都是 JSON Schema”仍不能保证零适配，为什么 MCP 不能替代模型能力、安全授权和业务校验；
5. 对真实项目做出 **采用 MCP / 直连 API / 暂缓并等待成熟** 的条件化决策，同时列出安全门槛、退出成本和可迁移资产。

### 0.3 受众与前置知识

适合：正在给 Agent 接工具的后端、平台、AI 应用开发者，以及需要评估集成协议的架构师和技术负责人。

需要：能读 JSON；理解 HTTP 请求、进程和基本权限概念；知道“模型生成工具调用请求”和“应用真正执行工具”不是一回事。不要求读过 MCP 全文，也不要求使用过本仓库。

## 1. 0–6 分钟｜先把口号改成可检验命题

### 板书

```text
MCP 是标准还是过渡方案？
              ↓
在哪一层成为标准？对谁的什么工作负载？在什么版本？
需要哪些外部控制？出现什么证据时应改判？
```

### 讲授内容

“标准”和“过渡”不是天然互斥。一个协议可以拥有开放治理和公开规范，同时仍是某个系统当前的过渡适配层；也可以暂时没有覆盖所有场景，却长期作为特定边界的通用协议。今天不争夺一个词，而是做四次限定：

1. **对象限定**：说的是规范文本、某个 SDK、某类 Server，还是完整企业平台？
2. **版本限定**：说的是 2025-11-25、2026-07-28，还是没有固定日期的“最新”？
3. **边界限定**：说的是模型选择工具、Client 调用 Server，还是 Agent 与 Agent 协作？
4. **证据限定**：说的是公告、代码存在、测试通过，还是跨团队真实互操作？

### 开场投票

让学员在纸上选择：`A 已是标准`、`B 主要是过渡`、`C 取决于层次与场景`。再补一句：“出现什么证据，我会改选？”本课程不记录真实投票结果；讲师现场执行时才填写结果。

**收束语**：没有反证条件的立场，通常只是偏好。课程结束时要交的是可修正判断，不是站队标签。

## 2. 6–16 分钟｜“成为标准”需要哪五层证据

### 2.1 本课的开放标准工作定义

本课把“开放标准”作为工程判断而非法律认证，观察四类特征：

- 规范公开、版本明确，变更可以审阅；
- 不被单一实现完全等同，存在独立实现的可能性与现实；
- 有公开治理、提案、弃用和兼容流程；
- 有一致性验证机制，能发现实现偏离，而不只比较 Logo。

这不是宣称 MCP 等同于某个特定国际标准组织的正式标准，也不是给出永久地位保证。公开治理与 AAIF 的形成支持“开放标准”判断，参见 S15–S17、S21；但它们不是互操作证明。

### 2.2 五层证据梯

| 层 | 应该问什么 | 能支持的结论 | 不能单独推出 |
| --- | --- | --- | --- |
| ① 协议规范 | 字段、错误、生命周期是否公开且版本化？ | 存在可审阅的共同语言 | 所有实现都完整、正确 |
| ② SDK / 实现 | 谁维护？支持哪个版本和哪些能力？有无分级与测试？ | 某语言可实现某些协议能力 | 所有 SDK 行为一致 |
| ③ Server 生态 | Server 是否可发现、维护、审查？版本和质量怎样？ | 有可复用集成供给 | 每个 Server 安全、活跃、可互通 |
| ④ 企业采用 | 是否进入真实权限、审计、采购和运维流程？ | 组织愿意承担采用成本 | 技术互操作已经验证 |
| ⑤ 实际互操作 | 哪些 Client×Server×版本×能力组合通过何种测试？ | 对受测组合作出有边界判断 | 未测组合、未来版本或整个行业 |

### 2.3 证据不能跨层搬运

- “官网列出 SDK”是第二层证据；SDK tiers 恰好提醒功能完整度和维护承诺存在差异（S18、S19）。
- “Registry 可发现”是第三层证据；namespace 验证不等于代码安全审计（S20）。
- “基金会公告”主要是治理与行业协作证据；不能直接填到第五层（S21）。
- “本仓库连通过一个 Server”只是特定组合的第五层实验；不能写成“MCP 生态全部兼容”。
- “模型能选对工具”还是另一项模型/宿主评测，不属于协议一致性的替代指标。

### 快速互动：把宣传语放回证据层

依次读出四句：

1. “规范里定义了 `outputSchema`。”——第一层。
2. “某语言 SDK 已发布。”——第二层。
3. “某 Server 在 Registry 有条目。”——第三层。
4. “两个具体实现在固定版本下完成工具调用。”——受测组合的第五层。

追问：“哪一句能证明企业生产安全？”答案是没有。生产安全还需要独立威胁建模、权限、审计和运行证据。

## 3. 16–28 分钟｜协议共同语言：连接、版本与能力

### 3.1 三个角色与一次调用的位置

```text
用户
  ↓
模型 / Agent 推理（选择什么、生成什么参数）
  ↓ 模型私有 API：如 function calling
Host 应用（策略、审批、上下文、Client 管理）
  ↓ MCP Client  ←—— JSON-RPC 2.0 ——→  MCP Server
                                        ↓
                                  业务 API / DB / 文件
```

依据 2025-11-25 架构（S01、S02）：Host 可管理多个 Client，Client 与 Server 通常是 1:1 连接。这个角色图不是部署安全边界图；Host 仍需决定哪个用户、哪个租户、哪个 Client 能做什么。

**关键分界线**：模型私有 function calling 位于“应用 ↔ 模型”，MCP 位于“应用/Agent ↔ 外部 Server”。前者可以让模型输出调用意图，后者让 Host 发现和调用外部能力；MCP 不替代模型推理，也不保证模型选对工具。

### 3.2 2025-11-25 生命周期

```text
Initialization                    Operation                 Shutdown
--------------                    ---------                 --------
Client → initialize               tools/list                stdio:
Server → initialize result        tools/call                关闭 stdin
Client → notifications/initialized ping / 已协商能力          等待进程退出
                                （未协商能力不得使用）         必要时 SIGTERM/SIGKILL
```

依据 S03、S04。必须区分：

- **协议版本协商**：双方能否用同一套协议语义交流；
- **能力协商**：在这个版本下，双方声明并允许使用哪些功能，例如 Tools、Resources、Prompts；
- **业务授权**：这个用户对这笔数据或这个副作用是否有权操作。

三次“允许”不能相互替代。版本相同不代表支持 Resources；Server 声明 Tools 不代表用户有权调用每一个 Tool；模型生成参数也不代表 Host 已批准执行。

### 3.3 版本演进不是脚注，而是架构成本

访问日 2026-11-12，S11 的 `/specification/latest` 实际跳转到 **2026-07-28**。本课用下表做有限对照：

| 观察点 | 2025-11-25 | 2026-07-28 规范所述方向 |
| --- | --- | --- |
| 请求模型 | 包含有状态连接与初始化阶段 | 强调 stateless、self-contained requests |
| 能力协商 | 初始化时协商 | per-request capability negotiation 等机制 |
| 相关机制 | `initialize` / `initialized` 等 | `_meta`、`server/discover` 等 |
| 不支持版本 | 按该版本生命周期与错误规则处理 | 定义 `UnsupportedProtocolVersionError`，示例 code `-32022` |
| 兼容讨论 | 旧版自身规则 | Modern / Legacy / Dual-era 兼容矩阵 |

来源为 S03、S11、S12、S13。这里不是在课堂上要求背新字段，而是看到一个事实：**同一 MCP 名称下，状态模型和协商机制也可能演进。** 因此客户端分支、Server 声明、测试矩阵和运维文档都必须带版本。

S14 的页面标记与 S11 的 `latest` 解析在访问时存在“current”标识不完全一致。处理方法不是挑一个顺眼的页面，而是：引用明确版本、写访问日期、保留最终 URL、在升级前重读规范。

### 课堂检查

问：“Server 与 Client 都写 2025-11-25，是否就能调用 `resources/list`？”
答案：不能。还要看双方能力声明、实现是否支持以及本仓库适配层是否暴露；本课程仓库没有实现 Resources（S08）。

## 4. 28–40 分钟｜传输不是细节：stdio 与 Streamable HTTP

### 4.1 stdio：本地进程边界

2025-11-25 stdio 的核心课堂模型（S04）：

```text
Host / Client 进程                         Server 子进程
      │ stdin  ── 换行分隔 JSON-RPC ───────→ │
      │ stdout ←── 换行分隔 JSON-RPC ─────── │
      │ stderr ←── 可用日志（不是协议帧）──── │
```

- stdout 只放协议消息。任何调试 `print` 混入 stdout，都可能破坏帧解析。
- 消息以换行分隔，不是“启动一次进程只发送一个 JSON 文件”。
- 关闭时先关闭 stdin、等待退出，必要时再升级 SIGTERM/SIGKILL；不能假定子进程永远主动退出。
- 本地启动命令、参数、环境变量和工作目录都是供应链与凭证边界。不要向子进程无差别继承全部秘密。

适合：本地工具、开发环境、明确生命周期的一个 Server 子进程。代价：进程管理、平台差异、资源清理和本地权限。

### 4.2 Streamable HTTP：远程服务边界

依据 S04，讲授以下最小地图：

- 单一 MCP endpoint，主要用 POST；可选 GET/SSE 用于服务端流式消息；
- 可能涉及 `Mcp-Session-Id` 与 `MCP-Protocol-Version`；
- 要处理响应形式、断线恢复、会话终止、重放和重复消息；
- 必须考虑 Origin 校验、DNS rebinding、本地服务暴露、会话劫持和认证授权；
- “把 stdio 包一层 HTTP”并不会自动得到正确的远程 MCP 服务。

适合：集中部署、远程共享、已有 HTTP 基础设施的团队。代价：鉴权、会话、扩展、审计、网络失败与运维。

### 4.3 传输与会话的四个常见误判

| 误判 | 修正 |
| --- | --- |
| “JSON-RPC 一样，所以换传输零成本” | 帧、连接、会话、鉴权、错误和关闭语义都会变化 |
| “HTTP 有 OAuth，所以 stdio 自动同样工作” | 授权规范的适用范围和本地进程凭证要分别设计，见 S05 |
| “断线后原请求自动重发最可靠” | 响应丢失不代表未执行，副作用工具可能重复执行 |
| “会话 ID 就是用户身份” | 会话关联不等于用户认证，更不等于业务授权 |

### 小组练习

场景 A：开发者笔记本上的只读文件搜索。
场景 B：多个团队共享、需要统一权限和审计的订单查询。

每组选择 stdio 或 Streamable HTTP，并写出两项收益、两项新增风险、一个关闭/恢复测试。参考判断见[练习 E3](d040-exercises.md)。选择不是唯一答案，但理由必须对应部署边界。

## 5. 40–50 分钟｜相邻协议与 Schema：标准化不等于零适配

### 5.1 function calling：模型接口，不是 MCP 的同义词

OpenAI Function calling 文档（S23）展示的典型循环是：

```text
应用把 type/name/description/parameters/strict 等工具定义交给模型
  → 模型生成 function_call
  → 应用自己执行函数
  → 应用把 function_call_output 回给模型
```

MCP 可以帮助应用从外部 Server 发现并取得工具，但模型仍需要自己的工具表示，应用仍要决定执行、审批和结果回喂。MCP 成功不等于模型推理成功；模型能生成合法 JSON 也不等于 MCP Server 互通。

OpenAI Agents JS 的 MCP 文档（S24）提供了直接反证“零适配”的实例：SDK 会把 MCP tools 转为 function tools，并处理 schema conversion、缓存、名称前缀、过滤和审批。`convertSchemasToStrict` 是 **best-effort**，转换失败时保留原 schema。这里不是在评价某厂商好坏，而是观察真实工程中确实存在的翻译层。

### 5.2 同名 JSON Schema，不等于相同契约

| 比较点 | 必须核实的问题 |
| --- | --- |
| dialect / 版本 | 双方实际接受哪个 JSON Schema 方言？ |
| 关键字子集 | `oneOf`、`anyOf`、`$ref`、默认值、嵌套组合是否都支持？ |
| strict 约束 | 是否要求额外字段禁止、所有字段必填或特定可空表示？ |
| 校验位置 | SDK、Client、Server、业务 Handler 各自校验什么？ |
| 结果信封 | `content`、`structuredContent`、`isError` 如何映射到模型私有结果？ |
| 语义 | 字段合法是否满足租户、状态机、金额、幂等等业务不变量？ |

“通过 JSON Schema 校验”只证明某个校验器接受了参数形状，不证明业务允许，更不证明模型私有接口与 MCP 使用完全相同的 Schema 处理规则。

### 5.3 REST/OpenAPI：不是落后的替代品，而是另一种合理边界

OpenAPI 是语言无关的 HTTP API 描述规范（S25）。对于少量、稳定、内部维护的 API，直接 REST/OpenAPI 调用可能具有：

- 依赖少、调用链短、调试熟悉；
- 现有鉴权、网关、监控和客户端生成可直接复用；
- 不需要额外的 MCP 会话、发现和结果转换。

MCP 的潜在价值是统一发现、统一调用和接入 Agent 生态；但它不会自动消灭业务字段映射、权限和错误语义。应比较总成本，而不是比较协议新旧。

### 5.4 A2A：只划边界，不跑题

依据 S26–S28：MCP 主要处理 Agent 到工具/资源的连接；A2A 主要处理独立、opaque Agent 之间的协作，核心包括 Agent Card、Task、Message、Part、Artifact。一个系统可以用 A2A 委托另一个 Agent，再由后者通过 MCP 使用工具。二者可组合，不是同一层的替代票选。

### 边界图收束

```text
模型私有 function calling：模型怎样表达调用意图
MCP：Host/Client 怎样发现并使用外部工具、资源、提示等能力
REST/OpenAPI：业务 HTTP API 怎样描述和被直接调用
A2A：独立 Agent 怎样发现、通信并围绕任务协作
```

## 6. 56–66 分钟｜标准化不等于安全边界

### 6.1 先分清四句话

1. **认证**：对面是谁？
2. **授权**：这个身份能做什么？
3. **业务权限**：这个租户、对象、状态和金额是否允许？
4. **用户同意**：本次具体副作用是否被人或策略明确批准？

MCP 规范可以描述安全要求和机制，但不能 magically 在任意 Host、Server 和业务系统里强制执行这些原则。OAuth token 不是业务权限；工具描述不是审批；模型说“用户同意了”也不是可信凭证。

### 6.2 威胁地图：协议之外必须有的控制

| 威胁 | 为什么不能只靠 MCP 字段 | 最低控制示例 |
| --- | --- | --- |
| Confused deputy | Server 有权限不代表它应替所有调用方行使该权限 | 明确受众与委托链、按用户/租户授权、拒绝混用 token |
| Token passthrough | 把某受众的 token 透传给另一服务会破坏边界 | 校验 issuer/audience/scope，使用合适交换或独立凭证 |
| Session hijacking | 会话标识被拿到后可能冒用连接 | 安全生成与绑定、传输保护、终止与轮换，见 S04、S06 |
| Prompt injection | 工具描述、资源或输出可能带不可信指令 | 内容分级、最小上下文、审批、输出过滤、不可把文本当授权 |
| 本地 Server compromise | 子进程能访问本机文件与环境 | 固定可信命令、最小环境、文件/网络隔离、资源限额 |
| 过宽 scope | 技术上可调用不等于任务需要 | 默认拒绝、最小 scope、短期凭证、按工具/动作细分 |
| 供应链与 Registry 误信 | 名称和 namespace 不证明代码无恶意 | 锁版本与摘要、审查依赖/安装脚本、扫描、签名与来源策略 |
| 副作用重放 | 超时或断线无法说明是否执行 | 幂等键、事实查询、对账、人工确认，禁止盲目自动重放 |

S06 给出多类 MCP 安全最佳实践；S20 说明 Registry 的身份/元数据与代码扫描责任边界。课程只给控制起点，不声称一张表能替代完整威胁建模。

### 6.3 Tools 的可信度边界

依据 S07：Tools 可有描述、`inputSchema`、可选 `outputSchema`、结果 `content` / `structuredContent`、`isError` 和 annotations。讲授三条限制：

- 描述和 annotations 默认不是可信授权声明；它们可能不完整、错误或来自不可信来源。
- `isError=true` 是工具结果语义，不等于传输断开；两者应走不同恢复策略。
- 支持某个规范字段与业务正确使用它是两件事；本仓库的结果适配范围比完整规范更窄。

### 互动：哪一个控制仍缺失

给出假想配置：“Server 有有效 OAuth token；工具 annotation 标为只读；Registry namespace 已验证。”要求学员说出仍不能推出的三件事。参考：不能推出该用户有权读此租户、不能推出工具实际无副作用、不能推出代码供应链安全。

## 7. 66–76 分钟｜治理与生态：正反方都必须过证据门

### 7.1 “正在形成持久开放标准”的论据

1. **公开版本化规范**：可以针对明确版本实现、评审和测试，而不是只能依赖单一私有 SDK（S01–S10）。
2. **公开治理与演进路径**：治理、SEP、Feature Lifecycle 让变更和弃用具有公共程序（S15–S17）。
3. **实现与一致性意识**：SDK tiers 和 conformance 讨论承认可移植性需要验证，而非只宣布支持（S18、S19）。
4. **跨组织协作**：Linux Foundation 于 2025-12-09 宣布 AAIF，MCP 是创始贡献项目之一（S21）。
5. **问题具有长期性**：Agent 需要发现、描述并调用外部能力，这个集成问题不会因某一家模型接口升级而消失。

这些论据支持“MCP 具备开放标准的重要条件”，仍不证明每个实现成熟。

### 7.2 “可能成为过渡方案”的论据

1. **协议本身在显著演进**：2025-11-25 到 2026-07-28 的状态和协商变化会产生真实迁移工作（S03、S12）。
2. **标准化并未消除翻译**：模型工具 Schema、结果信封、缓存、名称与审批仍需适配（S24）。
3. **传输和安全成本高**：本地进程与远程 HTTP 各自引入生命周期、会话和权限工作。
4. **生态质量不均**：SDK 分级、Server 维护差异和 Registry 边界意味着可发现不等于可依赖。
5. **简单场景可能不需要它**：少量稳定内部 API 用直连更简单；未来模型平台或其他协议也可能提供足够合适的边界。
6. **业务语义仍是私有成本**：订单状态、租户权限、幂等和审计无法靠统一传输自动标准化。

### 7.3 结构化辩论

每组必须完成四句话：

```text
我方结论适用于 ______（工作负载 / 版本 / 组织约束）。
我方最强证据是 ______，它位于五层中的第 ______ 层。
对方在 ______ 条件下可能更合理。
如果出现 ______ 可观察证据，我方愿意改判。
```

**正方合格反证例**：如果目标组合在固定版本的一致性测试、权限审计和迁移测试中持续失败，且适配成本超过直连，应重新评估。
**反方合格反证例**：如果独立实现能稳定互通，升级路径可预测，业务 Handler 与策略能跨协议复用，则“一次性私有适配”的论点会减弱。

这些是示例判定条件，不是真实行业测量结果。

补充事实：D039 的 [`evidence/d039-transcript.txt`](../evidence/d039-transcript.txt) 是 D039 终端证据，不属于 D040 授课记录。本课程没有录制或伪造 D040 transcript。

### 8.2 代码研讨三问

1. **统一层的价值在哪里？** Client 可以用相同的 list/call 路径发现与调用远端工具，本地 Registry 获得统一 Tool 形状。
2. **适配成本在哪里？** `mcp-tool.ts` 仍需转换描述、参数和结果；`mcp-stdio-client.ts` 仍需处理进程、请求 id、超时与关闭。
3. **哪些资产可离开 MCP？** 文件系统业务后端、参数校验思想、权限/审计规则、测试夹具和领域文档不应绑定在 JSON-RPC 传输上。

### 8.3 未实现能力清单

- Streamable HTTP、HTTP 会话与对应 OAuth 流程；
- Resources、Prompts 以及规范中其他未接入能力；
- 2026-07-28 的 `_meta` 每请求能力协商、`server/discover`、Modern/Legacy/Dual-era 兼容逻辑；
- 完整 `outputSchema` / structured content 生态、任意 SDK 方言自动转换；
- 生产级服务发现、Registry 审核、供应链扫描、统一身份和多租户授权；
- 通用自动重连、任意副作用请求的安全重放。

“未实现”是范围声明，不是说这些能力在 MCP 规范中不存在。

## 9. 84–90 分钟｜条件化决策与退出成本

### 9.1 三选一决策清单

不要先问“MCP 火不火”，按顺序回答以下问题。任何安全项不满足，都应先停止生产放量，而不是用生态热度抵消。

| 问题 | 倾向 MCP | 倾向直连 API | 倾向暂缓/等待成熟 |
| --- | --- | --- | --- |
| 集成数量与变化 | 多方工具、需要统一发现和复用 | 少量稳定内部 API | 需求仍频繁变化，边界未弄清 |
| 目标组合证据 | 固定 Client×Server×版本已通过测试 | 现有 HTTP 契约与测试已可靠 | 关键版本/能力组合未验证 |
| 传输匹配 | stdio 或 HTTP 与部署边界一致 | 现有网关/IPC 已足够 | 会话、传输或部署模型无法满足 |
| Schema 与错误 | 转换、校验和结果映射可控 | 无需额外翻译层 | 关键类型/失败语义无法可靠映射 |
| 安全与权限 | 能独立实现认证、授权、审批、审计 | 现有 API 安全链更成熟 | 无法满足最小权限或供应链要求 |
| 运维能力 | 能承担子进程或远程会话运维 | 现有服务监控足够 | 无法处理升级、断线、兼容与回滚 |
| 退出成本 | 业务资产与协议层已分离 | 私有 SDK 锁定成本可接受 | 无法保留 Handler、测试或策略资产 |

### 9.2 可直接使用的决策句式

```text
在【明确版本】和【这些能力/传输】下，
我们为【工作负载】选择【MCP / 直连 / 暂缓】，
因为【两项可验证收益】大于【两项实际成本】。
上线前必须通过【互操作、安全、失败恢复】测试。
如果【可观察反证】出现，我们将切换到【备选路径】，
并保留【业务 Handler、Schema、策略、测试】。
```

示例（教学虚构，不是采购建议）：若一个团队只有两个稳定内部只读 API、没有外部 Server 复用需求，现有 OpenAPI 客户端和权限审计均已工作，则先直连是合理选择；若未来需要跨团队统一发现，可在保留业务 Handler 的前提下增加 MCP 边界。

### 9.3 换掉 MCP 时，哪些资产仍能保留

| 项目资产 | 可迁移性 | 迁移动作 |
| --- | --- | --- |
| 业务 Tool Handler | 高，前提是输入/输出与协议类型解耦 | 保留领域函数，换一个薄调用入口 |
| 领域 Schema 与业务校验 | 较高 | 保留规范源，重新生成/转换目标接口 Schema |
| 权限、租户、审批策略 | 高，语义应独立于 MCP | 重新绑定目标协议的认证身份和调用上下文 |
| 幂等、超时、重试、对账规则 | 高，但触发点需重接 | 保留业务幂等键和事实查询，重写传输恢复编排 |
| 审计事件与业务指标 | 较高 | 保留事件语义，替换协议字段和 trace 关联 |
| 测试夹具与领域黄金用例 | 高 | 保留输入/期望结果，替换传输测试壳 |
| 业务文档与失败目录 | 高 | 更新调用图和协议术语，保留业务语义 |
| stdio 进程与 HTTP 会话代码 | 低 | 通常替换，不强行抽象成无成本通用层 |
| 初始化、发现、版本/能力协商 | 低 | 按新协议重写并重新验证 |
| MCP 特定结果信封与 SDK 类型 | 低到中 | 在适配层集中替换，避免渗入业务层 |
| MCP Server 配置与部署脚本 | 低到中 | 可复用环境思路，具体配置需重做 |

**架构建议不是“永远不绑定”**，而是把绑定集中在可审查的薄适配层；过度设计一个能兼容所有未来协议的框架，同样会浪费成本。

### 9.4 离场总结

```text
开放规范 ≠ 所有实现一致
存在 SDK ≠ 完整支持
Server 可发现 ≠ 安全可信
版本相同 ≠ 已协商能力
Schema 同名 ≠ 零转换
通过校验 ≠ 业务授权
支持 MCP ≠ 模型会选择
仓库 Demo ≠ 行业互操作
成为标准 ≠ 对每个团队都值得采用
成为过渡层 ≠ 没有长期工程价值
```

最终结论：**把 MCP 当作一个可评估、可测试、可替换的集成边界，而不是信仰或临时脚本。** 是否采用应由明确版本下的互操作、安全和总拥有成本决定。
