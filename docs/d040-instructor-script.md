> “我先给结论，但不急着让大家同意：MCP 已具备开放标准的重要特征，同时也可能是某些团队的过渡集成层。这两句话不矛盾。公开规范、公开治理是一种证据；你的系统是否值得采用，是另一项工程判断。
>
> “今天不比较谁更流行，不提供绝对投资建议，也不会拿一个仓库 Demo 推断整个行业。我们要做的是把口号改成能验证、能否定、能修正的命题。”


## 6–16 分钟｜五层证据：别把 Logo 当互操作

【板书】五列：`规范 / 实现 / 生态 / 采用 / 互操作`。

> “先定义今天说的‘开放标准’。我们观察四件事：规范是否公开和版本化；是否允许并存在独立实现；治理、提案和弃用是否公开；是否有一致性验证。这个工作定义不等于宣称 MCP 是某个国际标准组织颁发的永久认证。
>
> “接下来请守住五层证据。第一层是协议规范。规范写了 `resources/list`，能证明规范存在这个定义，不能证明某个 SDK 已经实现。
>
> “第二层是 SDK 和实现。官网列出 SDK，证明有实现入口。官方还给出 SDK tiers，讨论功能完整度、维护承诺和 conformance。也就是说，‘有 SDK’和‘所有 SDK 一致’不是同一句话。
>
> “第三层是 Server 生态。Registry 可以帮助发现，但可发现不等于高质量，更不等于安全。namespace 验证说明某些发布身份或来源声明经过验证，不是给代码做完整安全审计。
>
> “第四层是企业采用。企业宣布支持或进入基金会是重要信号，但企业采购公告不能替你做跨实现测试。
>
> “第五层是实际互操作。这里的问题最具体：哪个 Client、哪个 Server、哪个协议版本、哪种传输、哪些能力，跑了什么测试？只有通过了的组合才有直接证据，未测组合仍然未测。”

【投影】四句宣传语，逐条提问：

> “第一句，‘规范定义了 outputSchema’，在哪一层？”

【等待】预期回答：第一层。

> “第二句，‘某语言 SDK 已发布’？”

预期：第二层。

> “第三句，‘某 Server 在 Registry 有条目’？”

预期：第三层。

> “第四句，‘两个具体实现在固定版本下完成 tools/call’？”

预期：受测组合的第五层。

> “哪一句能单独证明企业生产安全？”

预期：没有。

无回应兜底：

> “如果不好记，只记一句：规范写得出，不表示实现做得全；实现跑得通，不表示生态都相同；生态数量多，不表示业务权限正确。”

【收束】

> “所以‘MCP 是标准吗’首先要改写成‘哪一层有什么证据’。”

## 16–28 分钟｜协议基线：版本、能力和授权是三道门

【投影】Host–Client–Server 图。

> “现在把调用位置画清楚。模型负责推理和生成调用意图。Host 应用管理上下文、策略、审批和 Client。MCP Client 与 MCP Server 通过 JSON-RPC 2.0 交流，Server 后面才是文件、数据库或业务 API。
>
> “按 2025-11-25 架构，Host 可以管理多个 Client，Client 和 Server 通常是一对一连接。请注意，角色图不是安全边界图。图画得整齐，不会自动产生租户隔离。”

【板书】

```text
模型：想调用什么
MCP：怎样发现和调用外部能力
业务权限：这次是否允许
```

> “2025-11-25 的生命周期先有 Initialization。Client 发 `initialize`，Server 返回结果，Client 再发 `notifications/initialized`，然后进入 Operation，例如 `tools/list`、`tools/call` 和已协商能力。stdio 关闭时，要处理 stdin 关闭、等待退出，以及必要时的 SIGTERM 和 SIGKILL。
>
> “这里有三道容易混淆的门。第一道是协议版本：双方是否说同一种协议语义。第二道是能力：双方都支持 Tools 吗，支持 Resources 吗。第三道是业务授权：这个用户是否能对这个对象执行这个动作。
>
> “现在问一个检查题：Client 和 Server 都写 2025-11-25，能不能直接调用 `resources/list`？”

【等待】预期：不能，还要看能力协商和实现。

> “对。版本相同不等于能力已协商，能力存在也不等于用户已授权。”

【投影】2025-11-25 与 2026-07-28 对照表。

> “再讲版本。本课程访问日是 2026-11-12。当天官方 `/specification/latest` 实际跳到 2026-07-28，而我们的仓库基线是 2025-11-25。后续版本强调 stateless、self-contained requests 和 per-request capability negotiation，并出现 `_meta`、`server/discover` 和 Modern/Legacy/Dual-era 兼容讨论。
>
> “大家不需要在这十分钟背下所有新字段。重要的是，同一 MCP 名称下，状态模型和协商方式会演进。不要拿 2025 年的初始化直觉解释所有后续版本，也不要把 2026 年的新机制写成旧仓库已经实现。
>
> “我们还观察到官方版本页的 current 标记和 latest 的解析不完全一致。工程上的处理不是替官网掩盖，也不是挑一个符合自己观点的页面，而是引用明确版本 URL、写访问日期、记录最终跳转。今天所有来源都做了这件事。”

【收束】

> “协议标准化减少的是共同语言的歧义，不会消灭版本管理和能力检查。”

## 28–40 分钟｜传输：本地子进程和远程服务不是同一份运维

【板书】stdio 图：stdin、stdout、stderr。

> “先看 stdio。Client 启动 Server 子进程，stdin 和 stdout 传换行分隔的 JSON-RPC 消息。stdout 只能放协议消息，日志应走 stderr。一个随意的调试打印，就可能让协议帧无法解析。
>
> “stdio 很适合本地工具和开发环境，但它不是‘没有运维’。启动命令是否可信？参数是否含秘密？环境变量是不是把父进程全部凭证都继承下去？子进程不退出怎么办？这些都是实际成本。
>
> “我们的关闭顺序是关闭 stdin、等待退出，必要时升级 SIGTERM 和 SIGKILL。这里不要背成所有远程 MCP 的通用关闭流程，它是 stdio 进程生命周期。”

【投影】Streamable HTTP 要点。

> “Streamable HTTP 把问题带到远程服务边界。2025-11-25 规范里有单一 MCP endpoint，主要 POST，可选 GET/SSE，还可能涉及 `Mcp-Session-Id` 和 `MCP-Protocol-Version`。现在必须考虑鉴权、Origin 校验、DNS rebinding、会话终止、断线恢复和重复消息。
>
> ‘用 HTTP 就更简单’只在某些基础设施上成立。它复用了网关和监控，也增加了网络、会话与身份问题。把 stdio 外面包一个 HTTP 端口，不等于自动实现正确传输。”

【板书】

```text
响应没回来 ≠ 请求没执行
会话 ID ≠ 用户身份 ≠ 业务授权
```

> “特别是断线。响应丢失不证明 Server 没执行。对有副作用的调用，自动重发可能写两次文件、创建两次订单。恢复要先看失败类型、幂等设计和事实查询，不是看到错误就 retry。”

【分组 3 分钟】

> “A 场景是开发者笔记本上的只读文件搜索；B 场景是多团队共享、需要统一权限审计的订单查询。每组选择一个传输，写两项收益、两项风险和一个关闭或恢复测试。答案可以不同，但理由必须来自部署边界。”

【邀请一组 40 秒汇报；无回应则按练习 E3 参考答案收束。】

> “本地只读搜索更容易用 stdio 控制生命周期；共享订单服务更常对应 HTTP，但必须继承成熟的身份、审计和网络安全。没有一句‘MCP 默认传输’能替你们做选择。”

## 40–50 分钟｜零适配神话：模型接口、OpenAPI 与 A2A

【投影】function calling 循环。

> “现在把 MCP 和模型私有 function calling 分开。以 OpenAI 文档为例，应用把工具名称、描述、parameters 和 strict 等定义交给模型；模型生成 `function_call`；应用执行函数；应用再把 `function_call_output` 回给模型。
>
> “MCP 在另一条边上：应用或 Agent 如何连接外部 Server。MCP 可以帮助发现工具，但不会替代模型推理，也不会保证模型选对工具。协议测试通过和模型任务成功率是两套评测。”

【板书】

```text
MCP Tool → SDK/Host 转换 → 模型工具定义
模型调用意图 → Host 审批/执行 → MCP tools/call
MCP 结果 → 结果映射 → 模型结果输入
```

> “OpenAI Agents JS 文档给了一个很具体的适配例子：它把 MCP tools 转为 function tools，还有 schema conversion、缓存、名称前缀、过滤和审批。`convertSchemasToStrict` 是 best-effort，失败时保留原 schema。
>
> “这就是‘标准化不等于零适配’的直接证据。双方都说 JSON Schema，也仍要核实 dialect、关键字子集、strict 约束、`$ref`、组合关键字、额外字段和结果信封。更不要忘记，Schema 合法只说明形状被接受，不说明租户、金额、状态机和幂等正确。”

【投影】REST/OpenAPI 与 A2A 边界。

> “直连 REST/OpenAPI 不是落后选项。两个稳定内部 API，如果现有 HTTP 客户端、鉴权、网关和监控都成熟，直连常常调用链更短。MCP 增加统一发现和 Agent 生态入口，也增加协议与适配成本。比较总成本，不比较新旧口号。
>
> “A2A 只花一分钟划边界。MCP 偏 Agent 到工具或资源；A2A 偏独立、opaque Agent 之间围绕 Task、Message、Artifact 等协作。一个 Agent 可以收到 A2A 任务后再通过 MCP 调工具。它们可以组合，不是同一层二选一。”

【快速提问】

> “如果模型这次选错工具，应该只检查 MCP Server 吗？”

预期：不应。还要检查模型工具描述、上下文、Host 转换、选择评测；Server 正确不能阻止模型误选。

## 56–66 分钟｜安全：协议不是授权系统

【板书】`认证 / 授权 / 业务权限 / 本次同意`。

> “欢迎回来。先区分四句话。认证回答‘是谁’，授权回答‘能做什么’，业务权限回答‘这个租户、对象、状态和金额是否允许’，用户同意回答‘这一次具体副作用是否被批准’。
>
> “OAuth token 不是业务权限。工具 description 不是审批记录。模型在文本里说‘用户同意’也不是可信凭证。MCP 规范可以定义机制和安全要求，但不能替任何 Host、Server 和业务系统自动执行这些原则。”

【投影】威胁地图。

> “第一，confused deputy。一个高权限 Server 不能因为它能做，就替每个调用方都做。必须知道原始用户、受众、租户和委托链。
>
> “第二，token passthrough。发给一个受众的 token，不应被不加判断地透传给另一个服务。检查 issuer、audience、scope，采用合适的凭证边界。
>
> “第三，session hijacking。会话标识是会话，不是用户身份。要保护生成、传输、绑定、轮换和终止。
>
> “第四，prompt injection。工具描述、资源和结果都可能带不可信指令。即使它写着‘忽略审批’，Host 也不能把这段文本升级成权限。
>
> “第五，本地子进程和供应链。可信启动命令、最小环境、依赖锁定、安装脚本审查和扫描都不能省。Registry namespace 验证不是代码安全背书。”

【互动】

> “回到休息前的问题：有效 OAuth token、只读 annotation、namespace 已验证，仍然不能推出什么？”

【等待，最多接受三项。】

无回应兜底：

> “至少有三项：不能推出这个用户能读这个租户；不能推出实现真的没有副作用；不能推出依赖和发布产物没有恶意。三个看起来正式的信号，分别没有替代业务授权、运行时验证和供应链审计。”

> “最后再分一种错误：`CallToolResult.isError=true` 是 Server 已返回的工具失败，不是传输断开。把它们混成一种错误，会让重连和重试策略失真。”

## 76–84 分钟｜仓库研讨：只证明一个子集

【投影】D034–D039 表格和代码路径。

> “现在回到本仓库，做一个证据边界练习。D035 到 D039 只实现并验证了 `2025-11-25 + stdio + tools` 子集。D035 是 Client，处理子进程、换行分隔帧、请求关联、初始化、能力检查、ping、tools/list、tools/call 和关闭。D036 是仓库内 Server 子集。D037 把远端 MCP Tool 适配成本地 Tool。D038 写使用与企业边界。D039 演示跨进程断开后创建新 Client，做一次独立的新调用，不重放失败请求。
>
> “请问，这一组代码能证明 MCP 全行业互通吗？”

预期：不能。

> “能证明 Streamable HTTP 已实现吗？”

预期：不能。

> “能证明 Resources、Prompts 或 2026-07-28 的 server/discover 已实现吗？”

预期：都不能。

> “那它能证明什么？它能证明这个仓库在明确版本和 stdio 下实现了一条 Tools 调用链，并且需要真实的适配代码。`mcp-tool.ts` 的存在本身就是‘标准化不等于零适配’的项目内证据。文件系统业务后端与传输分离，则说明替换协议时有资产可以保留。
>
> “D039 有真实终端 transcript，但它是 D039 的故障演示证据，不是 D040 公开课回放。D040 没有实际授课、视频或学员反馈，这个边界不能因为仓库里存在 txt 文件就被模糊。”

【快速书面任务】

> “请各写一项：已实现、未实现、不可外推。比如‘已实现 stdio tools/list’；‘未实现 Resources’；‘不可外推所有第三方 Server 的恢复行为’。”

## 84–90 分钟｜决策、迁移和退出题

【投影】三选一决策清单。

> “最后把判断变成行动。选择 MCP、直连 API，还是暂缓，按七个问题走：集成数量与变化；固定组合证据；传输匹配；Schema 和错误；安全权限；运维能力；退出成本。
>
> “如果关键安全项不满足，不是给 MCP 打低分然后继续上线，而是先停止生产放量。如果只有少数稳定内部 API，直连往往合理。如果需要多方工具复用、固定组合已验证、能承担安全和运维，MCP 更有吸引力。如果关键版本、能力和权限都无法验证，等待或做有边界试验比全面绑定更合理。”

【板书】可迁移资产与需替换资产。

> “换掉 MCP 时，业务 Handler、领域 Schema 和业务校验、租户权限、审批、幂等、审计语义、测试夹具与业务文档应尽量保留。传输、握手、发现、版本协商、结果信封和 SDK 特定类型通常需要替换。
>
> “所以架构目标不是发明一个兼容未来所有协议的巨型抽象，而是让绑定停在薄适配层，让业务函数不知道 JSON-RPC 帧长什么样。”

【退出题，学员独立完成 90 秒】

> “请写下三题答案。第一，为什么公开规范和基金会治理仍不能证明实际互操作？第二，为什么有效 OAuth token 和合法 JSON Schema 仍不能批准一笔业务写操作？第三，为你的项目选择 MCP、直连或暂缓，并写一个会改变决定的证据。”

【讲师可现场收集；未授课时不填写任何提交数量。】

> “今天的结论不是 MCP 必然胜利，也不是它必然被淘汰。它在开放标准和持续演进两条轨道上同时前进。对工程师最重要的是：固定版本，分层取证，独立建设安全边界，保留业务资产，并提前写好改判条件。谢谢大家。”
